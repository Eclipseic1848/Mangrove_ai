## 1.2. ZIP 展开边界

[#240](https://github.com/Eclipseic1848/Mangrove_ai/issues/240) 已经 [PR #258](https://github.com/Eclipseic1848/Mangrove_ai/pull/258) 合并并关闭（`56be854`）。该修复保留上传原件总量检查，把同次任务的全部 ZIP 与嵌套层级改为共享展开额度；内层 ZIP 容器、不支持解析的已展开成员及读取失败前已返回应用的字节也计入，不扫描或删除历史原件抵扣额度。

成员声明大小超出剩余额度时，在打开和写入前拒绝；读取时按至多 64KiB 分块，并以至多一个额外字节探测实际越界，超限成员不写盘。原路径、压缩比、成员数、深度和父子关系门保持。合法的已接受成员仍按原有部分拒绝语义处理。

经用户确认，只接受 STORED / DEFLATED 成员；BZIP2、LZMA 等其他方法在解码前记录 `zip_compression_unsupported` 并保留原包。标准库后两种解码路径不能用小块读取限制内部输出，不能据此承诺宿主硬内存上限。

#240–#243 的服务器代码及前端清单核对已确认集中移交 #244。#244 完成任务排空机制后统一对齐，此后逐票受控更新，最终发行仍须完成三端一致验收。

## 1.4. 就绪探针成本

[#242](https://github.com/Eclipseic1848/Mangrove_ai/issues/242) 将数据库探测改为同一连接内对两张接单必需表各执行一次 `SELECT 1 ... LIMIT 1`，不计数、不加载任务正文。数据库及三个可写根的结果在单进程内用单槽缓存复用，刷新完成后五秒到期；同一 Store 与根目录的并发请求只执行一轮探测，成功及失败都复用，到期后重新检查，不能沿用旧成功结果。

Worker 每次实时检查，退出即判为未就绪，不被资源缓存遮蔽；数据库或磁盘故障最迟在缓存到期后的下一次探测中反映。`/api/health` 仍为常量存活响应，readiness 返回 `Cache-Control: no-store`，不让下游缓存延长采样窗口。现有 Nginx 已关闭接口缓存并透传 200/503，无需修改代理模板。

上述边界限制的是查询读取量及昂贵检查的重复次数，不保证磁盘同步的硬耗时；SQLite 沿用既有五秒忙等待。服务器实际探针路径、代理策略及代码对齐仍由 #244 承接。

## 4. 已知问题与未验证范围

1. 仍有间歇性 Provider 结果未知，尚未证明根因已消除；不得盲目重发可能已执行的操作。
2. 部分在线任务仍会选择不合适的来源，或无法满足体裁、时效及输出要求；冻结来源评测不能代替在线采集验证。
3. 自然语言约束提取存在覆盖盲点，包括部分调度前缀和多工作表要求。
4. 前端仍有较大分块警告；弱网加载、真实读屏、手机软键盘和多用户容量尚未完整验证。
5. 构建、离线评测和 React Router 存在待处理依赖告警，详见[安全策略](../../SECURITY.md)。
6. 目标 Linux 环境、公网访问、备份恢复、外部来源和代表业务须在实际部署后验收。
7. Pi 与 CoreMind 尚无同题同条件性能对照；候选验证结果不用于两者排名。
