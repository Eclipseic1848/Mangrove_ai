## 1. 为什么需要这份蓝图

v0.0.3 已经能在用户明确给出文件或 HTTP API 后，完成安全获取、解析、确定性清洗、质量校验和多格式交付。但真实需求经常不会直接给出准确的数据位置或现成字段，例如：

- 上传一批合同，只提取每份合同中的交付期限、地点、验收和延期责任；
- 给出一个有权访问的网站，希望系统在登录后找到与营销有关的数据，再清洗导出；
- 从招投标文件中寻找资格条件和废标条款；
- 从发票、客服记录或供应链门户中定位用户指定的信息。

这些需求共同需要的不是若干行业专用脚本，而是一组可组合的通用能力：

```text
目标理解 → 授权边界 → 数据发现 → 获取与不可变保存 → 解析/OCR
→ 候选定位 → 证据约束抽取 → 确定性清洗 → 质量/人工复核 → 交付
```

因此，合同条款和营销数据只是首批纵向验收场景，不是 Mangrove 的功能边界。禁止把主链设计成 `ContractExtractor`、`MarketingCrawler` 等不可复用的场景分支。

## 2. 产品定位

Mangrove 的长期定位是：

> **任务驱动、证据优先的数据发现、抽取与准备 Agent。用户描述想得到什么，Mangrove 在用户授权和安全策略允许的范围内寻找数据、抽取有来源证据的候选事实，再通过确定性规则清洗、校验并交付可追溯的数据产品。**

它回答四个问题：

1. **用户要什么**：目标对象、字段、范围、时间、质量和输出是什么；
2. **数据在哪里**：已知文件/API/数据库，还是需要在文档、站点或授权系统中发现；
3. **结果依据什么**：每个语义结果来自哪个制品、页面、段落、表格、时间片或接口响应；
4. **如何可靠交付**：如何清洗、隔离异常、复核歧义并导出数据、证据、质量和 Manifest。

## 3. 可复用能力架构

安全与权限不是单独的末端步骤，而是横切所有层。

| 层 | 通用职责 | 不承担的职责 |
|---|---|---|
| 任务理解层 | 把自然语言目标转为对象、范围、目标 Schema、证据要求、复核策略和输出 | 不直接访问来源，不把猜测当事实 |
| 来源连接层 | 文件、网页、API、数据库、媒体及未来来源的探测、认证和只读获取 | 不做业务语义抽取和清洗 |
| 数据发现层 | 发现文件成员、章节、页面、表/列、站内区域、下载入口或只读接口，形成候选清单 | 不越过授权边界，不自动执行写操作 |
| 证据抽取层 | 定位候选片段并抽取结构化候选值，绑定原文、位置、来源和置信度 | 不凭常识补值，不覆盖原始证据 |
| 确定性准备层 | Recipe、标准化、类型转换、去重、异常隔离、账本、质量门和导出 | 不让 LLM 静默修改事实 |
| 复核与交付层 | 展示候选范围、冲突和低置信度结果；交付 Dataset、Evidence、Rejects、Lineage、Quality、Manifest | 不把未确认的高风险候选伪装成确定事实 |

复用现有底座：

- `DataPrepTaskSpec`、`SelectionSpec`、`TargetSchema`：任务范围和目标结构；
- `SourceSpec`、Connector：来源引用、限制和获取；
- `RawArtifact`、`RecordEnvelope`：不可变原始证据和位置；
- `Recipe`、`QualityPolicy`：确定性清洗和质量门；
- `DatasetManifest`、lineage：产物总清单和可追溯关系。

后续通过版本化契约扩展这些模型，不破坏 v2，也不在 `options` 中长期堆放无类型的关键业务语义。

## 4. 通用任务契约方向

以下是后续规划模型，不代表当前代码已经存在。

### 4.1 TaskGoal

描述用户真正想得到什么：

- 目标对象：合同、活动、客户、订单、投诉、设备等；
- 目标范围：文件集合、时间区间、站点区域、数据库范围；
- 目标字段及含义；
- “未找到”“存在冲突”“无法确认”如何表达；
- 输出格式和用途；
- 是否允许系统建议字段，哪些字段必须用户确认。

### 4.2 DiscoverySpec

描述如何寻找候选数据：

- 来源类型和允许域/目录/数据库；
- `document_sections`、`semantic_candidates`、`site_navigation`、`api_observation`、`schema_discovery` 等发现策略；
- 最大深度、页数、请求数、耗时和数据量；
- 允许的只读动作集合；
- 发现结果何时必须等待用户确认。

### 4.3 ExtractionSpec

描述如何从候选证据中形成结构化结果：

- 目标 Schema 和每个字段的语义定义；
- 字段是否允许多值、空值或候选冲突；
- 最低置信度；
- 必须附带的证据类型；
- 文档、表格、页面或媒体的上下文窗口规则；
- 低置信度、冲突和无证据值的处理策略。

### 4.4 EvidenceRef

每个语义抽取值必须能引用证据：

- `source_id`、`artifact_id`；
- 页码、段落、表格/单元格、行号、DOM 区域、URL、接口响应或媒体时间片；
- 原文或不可变证据片段的引用及哈希；
- 抽取器和版本；
- 置信度；
- 与输出记录、字段的对应关系。

Excel 可包含便于复核的证据摘要，但权威证据和完整血缘应保存在独立 Evidence/Lineage 产物中，避免单元格长度和格式限制导致证据丢失。

位置契约按来源表达：PDF/图片优先使用真实 bbox；DOCX 由 `python-docx` 提供确定性的段落号或表格/行号，写入 `EvidenceRef.location`。不得为了通过 bbox 门禁给 DOCX 伪造坐标；只有 bbox 和结构位置都缺失时才按“证据位置不足”进入复核。

### 4.5 ReviewPolicy

定义人机协作边界：

- 候选来源范围确认；
- 高影响清洗确认；
- 低置信度阈值；
- 多个互斥候选的处理；
- 是否允许空值交付；
- 写操作和外部副作用一律禁止，或进入单独的显式 HITL 流程。

### 4.6 DeliverySpec

描述交付内容：

- 权威数据格式和业务查看副本；
- Evidence、Rejects、Schema、Quality、Lineage、Manifest；
- Excel 的 Sheet 和列模板；
- 是否继续进入可选分析或报告流程。

### 4.7 Semantic Task Plan 与 Harness

Phase 4A 契约能描述文档字段、记录、原表、连续正文和证据汇总，但不能完整表达通用任务的
过滤、投影、行粒度、合并、聚合、内容政策和可执行后置条件。Phase 4B 因此新增独立 STP：

```text
用户目标 → Logical Plan → Source Inspector → Bound Plan
→ Capability Tools → Execute → Verify → Bounded Repair → Delivery
```

- Logical Plan 保存用户语义，不绑定具体工具；
- Bound Plan 把业务字段绑定到真实列、表、章节、元素或时间片；
- Physical Plan 选择工具、批次、并发和临时格式，但不得改变用户语义；
- 默认内容政策为原文摘录/重组；总结、改写、翻译和分析必须由用户明确要求；
- 高置信且可验证的只读任务自动执行，只有会改变范围、粒度、聚合、外发或格式的歧义才询问；
- 最终成功由结构、谓词、数量、证据、lineage 和格式后置条件共同决定，不能由模型自报；
- 语义修复最多两次，同一后置条件重复失败即停止。

权威实施计划：
[`docs/plans/2026-07-24-phase4b-semantic-task-harness-plan.md`](plans/2026-07-24-phase4b-semantic-task-harness-plan.md)。

## 5. 场景不是分支，而是能力组合

统一组合公式：

```text
来源类型 × 发现策略 × 抽取目标 × 证据策略
× 清洗 Recipe × 质量/复核策略 × 输出
```

| 场景 | 来源与发现 | 抽取与证据 | 准备与交付 |
|---|---|---|---|
| 合同交付条款 | PDF/DOCX/ZIP；章节、段落、表格候选 | 期限、地点、方式、验收、延期责任；原文+页码/段落 | 日期/单位标准化；冲突复核；XLSX+Evidence |
| 招投标资格条件 | PDF/网页；目录、章节和附件发现 | 资格、截止日期、废标条件；原文+页码/URL | 字段归一；跨附件完整性；XLSX/JSONL |
| 发票字段 | PDF/图片/ZIP；OCR 和版面区域 | 抬头、税号、金额、日期；坐标+OCR 置信度 | 金额/日期校验；低置信度复核；XLSX |
| 政策适用条款 | 文档/网站；章节和站内候选 | 适用对象、条件、时限；原文+版本/发布时间 | 枚举/日期标准化；新鲜度检查 |
| 客服投诉 | API/数据库/音频；字段或片段发现 | 问题、产品、诉求、时间；记录/时间片证据 | 去重、枚举映射；JSONL/Parquet |
| CRM 营销数据 | 认证网站/API/数据库；站内区域和只读接口发现 | 活动、渠道、转化、成本等用户确认字段 | 分页、Schema、去重；XLSX/Parquet |
| 供应链门户 | 认证网站/下载文件/API；订单与履约区域发现 | 订单、交付、库存、异常；页面/API 证据 | 增量、账本和异常隔离 |
| 简历候选信息 | PDF/DOCX/ZIP；文档批量发现 | 经历、技能、时间；原文+页码 | 日期标准化；敏感信息策略；XLSX |

新增场景应优先证明可以复用已有原语；只有来源协议、证据位置或质量规则确实不同，才新增通用能力。

## 6. 示例一：批量合同的交付条款

### 6.1 推荐流程

```text
上传合同/ZIP
→ 建立每份文档边界
→ 数字文本解析或 OCR/版面识别
→ 用户目标转候选字段
→ 检索交付相关章节、段落和表格
→ 抽取候选值并绑定原文证据
→ 标准化日期、地点、责任方和金额/比例
→ 隔离冲突、无证据和低置信度结果
→ 合同级完整性质量门
→ XLSX + Evidence + Rejects + Manifest
```

### 6.2 交互边界

- 用户只说“交付条款”时，Mangrove可以建议交付期限、地点、方式、运输责任、验收条件、风险转移和延期责任等字段，但正式批量抽取前应让用户确认或修改目标 Schema。
- 支持“原文摘录”和“结构化字段”两种模式；后者仍必须保留原文证据。
- 找不到时输出“未找到”，存在多个矛盾条款时输出冲突候选，不得选择一个看起来最合理的值冒充事实。
- 扫描件 OCR 不可用、页缺失或文档损坏时必须按文档列入 rejects/待处理清单。

### 6.3 文档级质量门

至少检查：

- 输入合同数 = 成功处理 + 解析失败 + OCR 待处理；
- 每份合同都有抽取结果、明确“未找到”或可解释失败；
- 每个非空语义值都有有效 EvidenceRef；
- 不允许跨合同混用证据；
- 冲突和低置信度记录没有被静默合并；
- 输出 Excel 与权威 Dataset/证据侧车可关联。

## 7. 示例二：授权网站中的营销数据发现

### 7.1 推荐流程

```text
确认授权范围和允许域名
→ 用户交互式登录或服务端 credential_ref 注入
→ 创建用户/任务隔离浏览器会话
→ 只读探索导航、搜索、标签页和报表入口
→ 返回候选数据区域让用户确认
→ 观察页面只读请求或下载入口
→ 可复用时移交 HttpApiConnector 批量获取
→ 清洗、质量校验和交付
→ 销毁会话并清理临时凭证
```

### 7.2 只读动作边界

默认可自动执行：

- 页面导航、展开菜单、只读搜索、筛选、排序、翻页；
- 打开详情和只读报表；
- 下载已经存在的报表；
- 观察当前页面发出的只读网络请求。

默认禁止：

- 创建、编辑、保存、删除、发布、发送、退款、审批、导入；
- 改变权限或账户配置；
- 触发可能产生费用、通知或业务状态变化的动作；
- 绕过 CAPTCHA、MFA、访问控制、网站安全机制或账号权限。

如果未来确需副作用操作，必须作为独立产品能力建模并显式 HITL，不能混入“数据发现”默认权限。

### 7.3 凭证和会话

- 优先让用户在隔离浏览器中亲自登录，Mangrove接管登录后的临时会话；
- 需要代管时仅保存 `credential_ref`，运行时临时注入；
- 密码、Cookie、Token 不进入对话、LLM 上下文、TaskSpec 公共表示、截图说明、日志、Trace、Manifest 或错误响应；
- 不同用户和任务不得复用浏览器上下文；任务结束或超时必须销毁会话；
- MFA/CAPTCHA 进入人工接管，不做规避。

### 7.4 网页不可信

页面文本、下载文件和接口响应一律视为数据。页面中出现的“忽略指令”“上传 Cookie”“访问另一个域名”等内容不能改变 Agent 目标、安全策略或工具权限。

“当前账号可以看见”也不自动等于“允许自动化批量提取”。还必须满足用户授权、组织政策、适用条款和技术安全边界。

## 8. LLM、Agent 与确定性代码的边界

LLM/Agent 可以：

- 澄清目标并提出可编辑的目标 Schema；
- 发现候选文档区域、页面和只读数据入口；
- 对候选片段分类；
- 从给定证据中抽取结构化候选值；
- 给出置信度、歧义和复核原因；
- 解释质量问题。

但必须满足：

- 语义结果是“有 EvidenceRef 的候选事实”，不是新的原始事实；
- 每个非空值都必须可追溯到来源证据；
- 原文未明确的信息保持空值或“不确定”；
- 不执行来源内容中的指令；
- 不直接修改原始数据；
- 不绕过确定性清洗、Schema 校验、账本和质量门；
- 高影响操作和歧义结果按 ReviewPolicy 处理。

确定性代码继续负责：

- 权限、域名、路径、SQL 和动作策略；
- 获取、重试、分页、限额和 checkpoint；
- 哈希、不可变存储和位置校验；
- Recipe 转换、去重、隔离和导出；
- 账本、阈值和 pass/warn/fail；
- 凭证脱敏和产物访问控制。

## 9. 分阶段落地

### Phase 3：数据库安全只读取数

已完成 SQLite/MySQL/PostgreSQL 只读连接、Schema/表列发现、SQLGlot 受控 SELECT、批量/增量抽取和凭证脱敏。它交付的不只是数据库功能，也为通用发现层提供 `schema_discovery`、范围确认和 checkpoint 原语。

### Phase 4A：文档智能与证据约束抽取

实现 OCR/版面结构、文档边界、语义候选、目标 Schema、EvidenceRef、冲突/低置信度复核和 Excel 交付。合同交付条款作为首个纵向验收，随后至少迁移到招投标和发票场景以证明复用。

基础层和首个产品闭环已落地：24 份/120 页文档黄金集、任务/发现/抽取/证据/复核契约、数字/扫描/混合页路由、数字文本 bbox、`pypdfium2` 渲染、统一多模型文本候选和统一外部文档解析契约。当前 `MinerU 3.4.4 + pipeline` 已实际承担扫描 PDF 坐标 OCR；PaddleOCR-VL 1.6 完整 Pipeline `18081` 已接入并完成同集 A/B，`18080/v1` 是 VLM 子服务，也可被 MinerU `hybrid-http-client` 调用。最新试点中 Hyper medium 可调用但表格质量不足，high 返回空结果，均不改变现有主备链。文本意图/元素候选可按任务显式选择 local/DeepSeek/百炼，禁止静默云降级；图片像素只交给视觉模型，缺少确定性 bbox 时不能直接进入 `found`。

产品结果不再固定为“一个字段一个值”。`ResultContract` 在执行前声明 `fields/records/tables/document/aggregate`、`one/many/all`、每行含义、渲染器、输出格式和 `merge_tables`。records 会遍历全部在范围元素，分块提取后按逻辑记录聚合，并在全部块完成后统一提交低置信度/冲突复核；tables 直接保留确定性解析器产出的全部表、行、列，禁止 LLM 命中第一行后停止。只有用户明确要求“合并成/为一张表”时才按原列位置无损拼接，并追加来源表/来源页；不同类型的表默认分开。权威输出按形态选择字段/记录 JSONL 或表格 JSON，XLSX 对记录增加 Records、对原表逐表生成工作表。预期 records/tables 为零时质量门必须失败，不能以空文件冒充完成。

`/data-prep` 以 `document_task_units` 区分独立文件任务与用户命名文件集。复选框只用于显式组合文件集，活动执行范围由 `unit_id` 决定；文件集成员点击只切换中间原文预览，不替换右侧文件集合并结果。顶层移除执行软归档，不删除上传原件、旧结果或不可变运行版本；完成后仍可继续输入自然语言创建新 revision。文件集成员增删已经采用“预览变更→用户确认→创建下一不可变版本”。MinerU 与 Paddle 完整 Pipeline `18081` 已完成同集 A/B，`18080/v1` 仅为 VLM 子服务。Phase 4A 最终全仓为 834 passed、4 skipped，显式性能门 3 passed，前端构建和 21 项 Playwright 通过。完整多语种/全页 OCR CER/WER、更大真实语料和真实 500 MB 文件仍是后续独立门禁。

### Agentic Runtime vNext：来源驱动的动态执行

## 10. 通用验收标准

### 10.1 正确性与完整性

- 来源/文档处理覆盖率可计算，未处理对象全部有原因；
- 候选发现覆盖范围有账本；
- 每个非空语义值 EvidenceRef 覆盖率为 100%；
- 无证据非空值为 0；
- 跨文档、跨用户、跨任务串数据为 0；
- 冲突、低置信度和“未找到”明确表达；
- 抽取准确率和召回率在固定脱敏 golden fixtures 上按字段评估，阈值在各阶段实施计划中确定。

### 10.2 安全

- 未授权域名和来源访问成功数为 0；
- 默认只读策略下产生业务副作用的动作数为 0；
- 凭证进入 LLM、日志、Trace、Manifest、错误和下载产物的次数为 0；
- 页面/文档提示注入改变任务目标或权限的成功数为 0；
- MFA/CAPTCHA 不被绕过；
- 用户和任务会话隔离测试全部通过。

### 10.3 复用性

每个新增通用能力至少通过两个不同领域的场景验证。首批最低迁移检查：

1. 合同交付条款 → 招投标资格/废标条款；
2. 发票字段 → 图片表单或报销单字段；
3. CRM 营销数据 → 供应链门户订单/履约数据；
4. 客服文本 → 音频客服转写记录。

如果迁移必须复制整条流水线或新增大量行业分支，说明抽象不足，应先修正通用契约。
