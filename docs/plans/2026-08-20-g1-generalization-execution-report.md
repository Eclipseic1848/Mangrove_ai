## 2. 实际执行的候选预检方法

每项最多进行 3 次完整 attempt。驱动只有同时满足以下条件才记为候选预检 PASS：

1. Pi Runtime 生成唯一、格式正确且可重新打开的候选；
2. 独立 Candidate Verifier 状态为 `passed`；
3. 当前冻结 `assertions.py` 对候选重放通过。

批次汇总只接纳目标文本与当前 `fixtures.json` 完全一致的本地模型结果；候选制品还使用当时
断言重新打开验证。该方法缺少正式 Delivery 发布与 QA，且若干断言只验证结构/长度/行数，
所以它只能用于诊断，不能替代 §5 的正式交付验收。

## 5. G1 发现并修复的代码缺陷

1. XLSX evidence locator 对 `sheet:<name> row:<n>` 贪婪匹配，把行号吞入 Sheet 名；改为
   非贪婪匹配并剥离行号后缀；
2. 工具表格说明行 `Table N: ... (R rows × C cols)` 不是来源事实；多行 grounding 跳过该行，
   剩余正文逐行严格命中，并复用既有 Markdown 竖线结构分隔规则；
3. 空 `results` 不能一律接受或一律抛错：只有 Relay 输入为 JSON 布尔 `true` 时才算明确
   `result_empty_confirmed`；字符串 `"false"`、`"true"` 或数字均失败关闭。明确空结果时仍由
   覆盖验证器检查所有候选是否已证据化排除。

公共接缝聚焦回归最初为 `35 passed`；双轴审查补出 Relay 布尔解析回归后，新增用例按 TDD
先红后绿，三文件聚焦集再次为 `35 passed`。审查前全仓后端回归为 `1655 passed, 5 skipped`，
最终一行失败关闭修复由上述聚焦集覆盖；前端 `npm.cmd run build` 通过。Python 编译、31/31
