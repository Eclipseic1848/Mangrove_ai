## 1. 结论

当前阶段不继续逐项打磨批次 7，也不扩展多媒体、网页、API、数据库或复合来源能力。
批次 8A 只做一件事：

> 用现有文档和表格能力，把“任务提交到正式交付”的统一闭环做成可验证、可诊断、
> 可安全失败并能由用户亲自验收的本机 PC 框架。

统一任务闭环为：

```text
任务提交 → 理解需求 → 制订计划 → 读取来源 → 执行 → 验证 → 正式交付
```

批次 8A 完成后，只能声明“本机框架工程验证通过”。服务器部署、10–20 用户压力测试、
GPU/Compose 验证和 Phase 4B 封板属于批次 8B，必须重新获得用户确认。

2026-07-28 执行结果：代码和自动化工程门禁已完成，真实本地模型编译、四类真实文件
HTTP/Worker/Delivery/重开闭环、完整 PC Playwright、OTLP→Phoenix 和失败门禁均已取证。
用户尚未按页面说明完成 Word → TXT 与 Excel → XLSX，因此不得写成“用户验收通过”。

## 2. 当前代码事实

1. 工作台已经持久化任务、revision 和事件，并有
   `queued/running/needs_input/cancelling/cancelled/failed/completed` 顶层状态。
2. 当前时间线会依据“已观察到更后阶段”推断前序完成；批次 8A 必须用权威事件和终态
   不变量验证，不能继续依赖可能失真的 UI 推断。
3. 当前编译阶段把所有非 `ready` 状态概括为“需要补充”，但真实编译失败未必存在可回答
   问题；这正是最新 Word 任务错误反馈失真的原因。
4. 当前失败记录主要是一个字符串，无法稳定提供失败阶段、尝试次数、处理影响、交付状态和
   错误编号。
5. 当前任务进入回收站 30 天后会删除工作台任务、revision 和事件聚合，但下层原文件、
   证据和交付继续保留；批次 8A 按 ADR-0015 增加精简审计记录。
6. 仓库已有 pytest、Hypothesis、Playwright、OpenTelemetry、Testcontainers 和公开脱敏
   DOCX/PDF/XLSX/CSV 夹具，不需要重建测试框架。
7. 本机 OpenTelemetry/Traceloop 实际安装版本与锁文件不一致，必须先对齐依赖事实。

## 3. 范围

### 3.1 本阶段实施

- 统一生命周期状态与事件不变量；
- 结构化、可持久化的用户失败说明和管理员诊断引用；
- 本地模型分阶段上下文预算、结构化编译非思考模式和有界停止；
- 长内容分块处理及覆盖账本；
- 输出格式冲突确认；
- 复合来源明确拒绝；
- 取消、幂等、权限和坏产物失败关闭；
- 精简审计记录；
- OpenTelemetry 七阶段最小 span；
- 可选本地 Phoenix Docker；
- 四类真实成功闭环和八类固定失败场景；
- Promptfoo 六案例隔离 PoC；
- 面向用户本人的简明验收清单。

### 3.2 本阶段不实施

- 文档与表格混合的复合来源执行；
- 网页、REST API、数据库新来源真实执行；
- Phase 4C 图片、音频和视频能力；
- 移动端或多浏览器适配；
- 工作台整体视觉重做和批次 7 非阻塞体验打磨；
- 管理员跨用户正文治理；
- 用户数据物理擦除；
- 服务器部署、多人压力和封板；
- `v0.0.6` 标签或新版本。

## 4. 目标架构

### 4.0 TDD 公共测试边界

批次 8A 只从以下已确认边界验证行为：

1. 工作台 HTTP API：创建、查询、补充、取消、版本和下载；
2. Playwright PC 页面：上传、提交、进度、失败说明、结果和下载；
3. 正式产物：下载后由独立读取器重开并机械比对；
4. OTLP 接收端：验证任务轨迹、错误码和脱敏属性；
5. `WebUIStore` 公开接口：验证精简审计记录，不允许测试绕过接口直接查询数据库表。

测试不得通过私有方法、内部调用次数或原始数据库旁路来证明用户行为。

### 4.1 权威状态与事件

保留现有任务、revision、Harness 和 Delivery 存储，不另起一套编排系统。批次 8A 只在
现有边界上补齐：

- 每个阶段明确的开始、成功、等待、失败、取消事件；
- 任意时刻最多一个活动阶段；
- 终态不能回退到运行态；
- 取消后不得发布 Delivery；
- 相同任务重复投递最多产生一份正式交付；
- UI 只根据权威事件计算进度，不因看到后序事件就无条件补全前序成功；
- 任务事件、OpenTelemetry span 和正式交付通过稳定身份关联。

### 4.2 失败契约

异步任务失败记录至少包含：

```text
error_code
stage
cause_summary
attempt_count
elapsed_ms
source_read
intermediate_created
delivery_published
next_actions
diagnostic_ref
```

普通用户看到全部可操作字段；管理员/开发者可通过 `diagnostic_ref` 查看 Token、模型参数、
逐次诊断、Worker 和技术堆栈。两层都不得复制业务正文或泄露其他用户信息。

### 4.3 本地模型与长内容

- Compiler 只读取任务要求、来源结构和必要摘要，不读取整份来源正文；
- 结构化编译关闭思考，设置显式输入/输出预算；
- 调用前进行预算预检，预计超限就分块；
- 文档执行按章节/元素批处理，并保存目标覆盖账本；
- 安全且唯一可推导的后置条件由确定性代码补齐；
- 涉及范围、内容政策、格式或结果含义的缺口暂停询问；
- 不同阶段可使用不同本地模型配置；
- 不允许静默切换到外部 API。

### 4.4 生产档案与观测

- 任务数据库、事件、Manifest、证据和制品哈希是权威生产档案；
- 普通用户查看自己的任务档案和用户失败说明；
- OpenTelemetry/Phoenix 是辅助诊断，不是业务事实源；
- Phoenix 不可用时业务继续运行；
- 工作台清理后保留不含正文、不可恢复的精简审计记录；
- 观测属性只保存任务/运行哈希、阶段、来源类型、数量、格式、模型、版本、耗时、状态、
  错误码、重试、计数和 QA 结果。

## 6. 实施批次

### 8A-0：基线与依赖事实

实施：

- 保存当前代码与测试基线；
- 显式区分项目改动、用户改动和运行期文件；
- 在隔离环境核对 OpenTelemetry/Traceloop 版本；
- 固定 Phoenix 镜像、Promptfoo 和 Node 工具版本；
- 建立快速测试、真实后端测试、真实模型测试三个明确层级。

退出门：

- 实际依赖版本与锁定记录一致；
- 现有回归基线可重复；
- Docker 或本地模型不可用时明确判为“未验收”，不能以 skip 冒充通过。

### 8A-1：生命周期、错误与阻塞项最小修复

实施：

- 先用 pytest/Hypothesis 固化生命周期不变量；
- 建立稳定错误编号和用户失败说明；
- 修正 `failed` 与 `needs_input` 混淆；
- 修正格式冲突的暂停确认；
- 明确拒绝复合来源；
- 落地精简审计记录；
- 对直接阻断闭环的批次 7 问题实施最小通用修复：
  - Compiler 非思考结构化调用；
  - 显式上下文与输出预算；
  - 安全后置条件确定性补齐；
  - 有界超时、重试和失败诊断。

退出门：

- 顶层状态和阶段状态无冲突；
- 失败、等待、取消和成功可机械区分；
- 取消后发布数为零；
- 重复投递正式交付数最多为一；
- 精简审计记录在工作台清理后仍存在且不含正文。

### 8A-2：任务轨迹与管理员诊断

实施：

- 增加 `workspace.task` 根 span；
- 增加 `compile/inspect/bind/execute/verify/publish/download` 七阶段 span；
- 跨后台 Worker 传播 trace 上下文；
- 对属性做允许列表和敏感信息测试；
- 增加可选 Phoenix Docker profile，固定版本、仅本机访问、关闭遥测和外部资源；
- exporter 失败时 fail-open，不影响业务任务。

退出门：

- 成功、等待、取消、失败任务都能定位实际停止阶段；
- trace 无正文、密钥、文件名、本机绝对路径和下载链接；
- Phoenix 停止后任务仍能完成；
- 任务档案与 trace 能通过稳定身份关联。

### 8A-3：四类真实成功闭环

串行执行：

| 输入 | 任务 | 正式交付 | 机械验收 |
| --- | --- | --- | --- |
| DOCX | 限定范围提取并汇总 | TXT | 范围、内容、编码、哈希 |
| PDF | 证据绑定的条款提取或核查 | DOCX/PDF | 证据、重开、页数、哈希 |
| XLSX | 筛选、保留指定列并排序 | XLSX | 行列集合、顺序、公式/值、重开 |
| CSV | 去重或分组汇总 | CSV/JSON | 记录集合、聚合回算、编码、重开 |

Playwright 负责证明真实用户从上传到下载完成操作；Python 验收器负责证明下载内容正确。
二者不能相互替代。

退出门：

- 四项均经过真实前端、真实后端、真实本地模型、Worker、验证、Delivery 和下载；
- 所有正式文件由独立读取器重开；
- 预期计划、证据范围和结果内容机械比对通过；
- Mock 测试不计入四项真实闭环。

### 8A-4：八类失败路径

真实用户路径：

1. 信息不足后补充并继续；
2. 用户随时取消；
3. 复合来源明确拒绝；
4. 输出格式冲突暂停确认。

受控故障注入：

1. 模型超时或输出截断；
2. 转换器崩溃或产物损坏；
3. 重复投递；
4. 跨用户访问。

退出门：

- 所有异常安全停止；
- 用户失败说明满足六项最低信息标准；
- 不发布假结果或损坏产物；
- 不出现无限重试；
- 其他用户无法读取任务、事件、诊断或下载；
- 故障只作用于隔离测试目录和测试任务。

### 8A-5：Promptfoo PoC

实施：

- 复用现有 `intents.json` 和 Python scorer；
- 通过薄 Python provider 调用真实 Compiler 或统一工作台 API；
- 覆盖四类成功计划、模型截断和复合来源拒绝，共六个案例；
- 使用 `--no-cache --no-share`；
- 结果只使用公开脱敏夹具，禁止上传真实业务内容。

退出门：

- 连续三次真实运行结果稳定；
- 缓存不能把失败伪装成通过；
- 不产生外部分享或敏感 trace；
- 与 pytest 的 P0 判定不冲突。

未达到上述条件时，PoC 保留为评测证据，不升级为强制门禁。实际连续三次均为 6/6，
但 provider 只验证接线和场景契约，仍不替代真实文件与真实模型门禁。

### 8A-6：全量收口与用户验收交接

实施：

- 全仓后端回归；
- 前端生产构建；
- 原 Mock Playwright 套件；
- 新增真实闭环 Playwright 套件；
- 四类正式产物重开；
- UTF-8、`git diff --check`、依赖一致性和脱敏检查；
- 更新权威计划、ADR、配置样例、执行报告、`AGENTS.md`、`handoff.md`；
- 输出一份面向用户本人的简明验收清单。

退出门：

- 工程门全部通过且无必需测试被 skip；
- 批次 7 非阻塞问题仍明确留在延期台账；
- 只允许声明“工程验证通过”；
- 用户按验收清单完成 DOCX → TXT 和至少一个表格任务并明确确认后，才能声明
  “用户验收通过”。

## 7. 用户验收清单的交付形态

工程验证完成后，提供一份无需命令行的短清单：

1. 打开哪个页面；
2. 上传哪个公开脱敏测试文件；
3. 复制哪一句任务要求；
4. 正常情况下每一步应显示什么；
5. 去哪里预览和下载；
6. 如何打开并核对结果；
7. 哪些现象算通过；
8. 失败时记录哪个任务编号、错误编号和截图。

它只教用户如何验收当前版本，不扩写为通用产品手册。

## 8. 预计难度与成本

| 工作 | 难度 | 预计有效工程量 |
| --- | --- | ---: |
| 依赖对齐与测试分层 | 中 | 1–2 人日 |
| 生命周期、错误契约、审计记录及阻塞修复 | 高 | 4–7 人日 |
| OpenTelemetry + Phoenix | 中高 | 3–5 人日 |
| 四类真实 Playwright 闭环和产物验收 | 高 | 5–8 人日 |
| 八类失败注入与权限/幂等门 | 高 | 3–5 人日 |
| Promptfoo PoC、文档和验收交接 | 中 | 3–5 人日 |

不含新发现业务缺陷时，预计总量约 **19–32 个有效工程人日**。其中已有工具接入本身约
14–22 人日，剩余预算用于当前已知阻塞修复、审计记录和收口。该数字是工程量估算，不是
自然日承诺；本地模型推理速度、真实闭环暴露的 P0 缺陷和依赖漂移可能增加时间。

为了控制成本，每个小批次独立出证据；若某一步发现需要扩大产品范围，立即停止并重新确认，
不把未知工作悄悄混入批次 8A。

## 9. 主要风险与控制

| 风险 | 控制 |
| --- | --- |
| 本地模型长思考或上下文截断 | 编译非思考、预算预检、分块覆盖、有界停止 |
| 真实 E2E 耗时和波动 | 串行运行、公开固定夹具、机械预期、禁止用 retry 掩盖失败 |
| 状态与 UI 再次失真 | 权威事件、不变量测试、最多一个活动阶段 |
| Trace 泄露正文或凭证 | 属性允许列表、公开夹具、脱敏门、Phoenix 仅本机 |
| Phoenix/Promptfoo 污染主环境 | Docker/隔离工具目录、固定版本、业务 fail-open |
| 工具增加但没有证明价值 | Promptfoo 先 PoC；Toxiproxy 按剩余风险再决定 |
| 批次 7 细节反向吞噬 8A | 只修阻塞闭环的通用问题，其余继续登记 |
| 工作区混入用户文件 | 显式白名单提交，禁止 `git add .` |

## 10. 提交、推送和版本边界

- 方案确认前不开始功能代码；
- 当前工作区混有用户/运行期改动，实施和发布必须使用显式文件白名单；
- 不提交 `.claude/settings.local.json`、`data/lessons/`、`data/templates/`、
  `.pytest-tmp/`、`frontend/test-results/` 或真实业务文件；
- 批次 8A 代码、测试、配置和相关说明在工程验证完成后统一提交并推送到
  `platform/v0.0.6`；
- 不创建或移动 `v0.0.6` 标签，不宣布 Phase 4B 封板；
- 用户验收发现问题时，继续留在 `v0.0.6` 做有界修复并追加证据。

## 11. 批次 8A 最终退出标准

只有以下条件同时满足，才能声明“工程验证通过”：

1. 依赖事实与锁定记录一致；
2. 生命周期、权限、取消、幂等、格式协商和失败关闭不变量通过；
3. 四类真实成功闭环及正式产物重开全部通过；
