> 状态：`engineering_verified_pending_user_acceptance`
> 实施证据：[DR-00–DR-07 执行报告](2026-07-31-agentic-runtime-coverage-aware-document-retrieval-execution-report.md)
> 本文不授权切换默认入口、发布版本或外发业务数据。

## 1. 问题与目标

真实扫描 PDF 任务暴露了两个相反风险：

1. 在 Pi 启动前对整份文件逐页做高质量 OCR，保证可读但局部任务等待过长；
2. 统一按“从前向后、字段齐全即停止”处理，局部任务较快但全量查询会漏掉后续页面。

本规格的目标是让 Pi 自主理解和完成用户目标，同时把权限、证据和“是否真的完成”放在
可验证的确定性完成门后：

```text
用户目标
→ Pi 形成覆盖契约草案
→ 校验并冻结业务约束
→ Pi 观察来源并自主调用能力工具
→ 覆盖账本记录已知与未知
→ Pi 提议停止
→ 独立 Verifier 决定通过或返回重规划
```

成功不以“Pi 已回答”判断，而以“结果满足覆盖契约且每项绑定权威证据”判断。

## 2. 已确认业务语义

### 2.1 覆盖契约不是固定路由

`CoverageContract` 是 Pi 对用户业务目标的结构化理解，不是根据关键词选择执行器的
`TaskFamily`。它由可组合维度构成：

| 维度 | 示例 | 语义 |
|---|---|---|
| 获准范围 | 整份附件、附件 2、第 20–30 页 | 最多允许读取什么 |
| 结果基数 | 首个、指定 10 项、全部 | 用户期望返回多少 |
| 完整性 | 严格完整、尽力而为 | 是否允许已知盲区 |
| 稳定顺序 | 文件顺序、页码、时间 | “首个”如何判定 |
| 对象边界 | 单据、表格、章节 | 一个完整结果从哪里开始和结束 |
| 停止语义 | 首个完整对象、全部候选已读 | 什么情况下可以提议结束 |

首个命中、指定范围、穷尽匹配和整源处理是常见规范化结果，不是四条固定流水线。禁止以
`if "所有" in query` 等字符串判断直接决定路线；词语只能作为 Pi 结合上下文理解意图的
信号之一。

对于“查找 XXX 的数据”等表达，Pi 高置信度时直接按理解执行，并在任务摘要中明确展示
“返回首个/指定数量/全部匹配”。如果不同解释会实质改变结果或资源成本且 Pi 置信度不足，
只提出一个澄清问题。产品可以倾向完整作为安全默认，但不能把它实现为问法路由表。

### 2.2 智能决策与确定性完成门

- Pi 负责理解目标、选择能力、安排顺序、根据 Observation 扩大读取或换能力；
- Pi 可以提议任务已完成，但不能自行签发完成结论；
- 覆盖账本只记录已观察、已权威读取、质量不足和仍未知的事实，不替 Pi 规划；
- Verifier 使用冻结契约和覆盖账本独立决定通过、返回重规划或失败关闭；
- 权限、Owner 隔离、外发边界和正式发布权始终由确定性机制控制。

### 2.3 发现不等于证据

- 来源发现索引负责召回，允许使用低成本、低分辨率或粗粒度表示；
- 证据读取集负责结果证明，必须来自可重开的原件和权威解析路径；
- Pi 可以根据发现索引选择精读范围，但不能把索引文本直接写成已验证来源事实；
- Verifier 必须脱离 Pi 的自我声明检查覆盖与证据。

## 3. Module 与 Interface

### 3.1 文档检索 Module

上一版单一 `retrieve(...)` 会把观察、发现、精读和停止策略一起藏进 Implementation，实际
削弱 Pi 的自主工具循环。本版改为三个能力级 Interface：

```python
inspect(source_snapshot: SourceSnapshotRef) -> SourceMap

discover(
    source_snapshot: SourceSnapshotRef,
    query: RetrievalQuery,
    scope: ScopeSelector,
) -> DiscoveryResult

read(
    source_snapshot: SourceSnapshotRef,
    unit_refs: list[ContentUnitRef],
    needs: EvidenceNeeds,
) -> EvidenceReadSet
```

Pi 决定何时检查来源、在哪个范围发现候选、何时精读以及需要文本、表格还是版面能力。
Interface 不暴露 OCR Provider、页面拆分、渲染分辨率、缓存目录、主备顺序和重试策略；这些
实现复杂度仍留在深 Module 内。

### 3.2 输入契约

Pi 生成的 `CoverageContract` 草案经确定性校验后冻结，最少包含：

```text
authorized_scope     获准文件、页、附件或章节范围
result_cardinality   first | count(n) | all
completeness         strict | best_effort
ordering             首个命中所依据的稳定顺序
required_fields      判定一个对象完整所需的字段/结构
object_boundary      单据、表格、章节等边界语义
stop_semantics       允许 Pi 提议停止所需的业务条件
interpretation       展示给用户的简短目标摘要
confidence           结构化理解置信状态，不保存隐藏思维链
```

`RetrievalQuery` 表达寻找什么，不包含 Provider 或 OCR 参数。

### 3.3 输出契约

文档检索能力调用分别返回 `SourceMap`、`DiscoveryResult` 或 `EvidenceReadSet`，并追加
`CoverageLedger`。账本最少包含：

```text
coverage_contract_id
authorized_unit_count
observed_unit_ids
authoritatively_read_unit_ids
low_quality_units[]
unknown_units[]
parser_versions[]
agent_stop_proposal
verifier_decision
verifier_gaps[]
```

`EvidenceReadSet` 最少包含：

```text
evidence_refs[]
source_unit_ids[]
quality_status
authoritative_parser_versions[]
```

不变量：

- 严格全部匹配或整源任务成功时，`unknown_units` 和未解决的 `low_quality_units` 必须为空；
- 每个非空结果项至少有一个 `evidence_ref`；
- 首个结果必须记录顺序证明和对象边界证明；
- 低质量发现页不能被当成“无匹配”，必须精读、换 Adapter 或失败关闭。

## 4. 执行策略

### 4.1 Pi 理解目标

Pi 读取当前要求、会话上下文和已确认约束，形成覆盖契约草案。校验器检查范围、权限、字段
完整性与内部矛盾；高置信度草案直接冻结并展示解释摘要，实质歧义才进入单问题澄清。

确定性校验器不得增加业务含义，也不得通过关键词重新解释 Pi 的草案。

### 4.2 来源观察

Pi 调用 `inspect` 获取文件身份、页数、数字文本层、页面图像占比、已有索引和可用能力。
这些 Observation 用于规划下一步，但不能改变冻结的业务范围。

### 4.3 Pi 自主发现与权威读取

Pi 自主决定调用 `discover`、`read` 的顺序、范围和循环：

- 可以先读数字文本、建立扫描页轻量索引，也可以直接精读明确指定的页面；
- 可以优先检查高概率页面，再根据覆盖账本继续扩大；
- 可以按任务需要选择文本、表格或版面能力，但不直接选择 Provider URL；
- 工具失败、空返回和低质量必须作为 Observation 返回，不能伪装成无匹配；
- 发现索引按 `owner + source_sha256 + discovery_version` 隔离，跨用户不可见；
- 对严格全部匹配，最终必须让全部获准内容单元参与可信发现；
- 对首个完整对象，形成顺序、边界和必需字段证据后可以提议早停。

低成本发现加候选页精读是扫描大文档的推荐策略，但不是系统写死的每任务流水线。Pi 可以
根据来源情况采用其他能力组合，只要不放宽覆盖契约并能通过完成门。

### 4.4 覆盖账本与完成门

每次 `inspect`、`discover` 和 `read` 都更新覆盖账本。Pi 根据账本继续重规划；当它认为目标
已经满足时提交停止提议。独立 Verifier 随后检查：

- 覆盖账本是否满足冻结契约；
- 所有结果项是否有权威证据；
- 未知或低质量单元是否与完整性等级冲突；
- 首个对象是否具有稳定顺序和边界证明；
- 停止提议是否静默改变范围、数量或结果含义。

未通过时把结构化缺口作为 Observation 返回 Pi 有界重规划。Pi 仍不能扩大未授权来源、放宽
完整性、自动外发或把发现索引当最终证据。

## 5. 状态与 UI 反馈

后台事件与前端业务阶段使用同一词表，避免任务实际运行但页面显示 `0/8`：

| 业务阶段 | 用户可见文案示例 | 必须提供的进度 |
|---|---|---|
| `goal_interpretation` | 已理解为：返回整份文件中的全部匹配项 | 范围、数量、完整性摘要 |
| `source_probe` | 正在识别文件结构 | 文件数、页数 |
| `source_discovery` | 正在检查全部 109 页以避免遗漏 | 已发现页/总页数、缓存命中数 |
| `evidence_read` | 正在精读 7 个候选页面 | 已精读候选/候选总数 |
| `agent_execute` | 正在整理并生成结果 | 当前动作摘要 |
| `verify_coverage` | 正在核对是否存在漏页或漏项 | 覆盖页、未覆盖页、证据项 |

局部任务应明确显示“找到第一个完整单据后停止”；全量任务应明确显示“将检查全部页面”。
高置信度理解不增加一次确认点击，但用户可以在任务详情看到冻结摘要；实质歧义仍只问一个
问题。界面只展示动作摘要和覆盖事实，不展示隐藏思维链。刷新或断线重连后必须从持久化
事件恢复真实阶段，不得回到“尚未开始”。

## 6. 失败关闭

以下情况不得生成“已完成”候选：

- 穷尽/整源任务存在未发现页面；
- 发现质量不足且权威解析无法补齐；
- 首个对象边界或必需字段未确认；
- 候选页完成发现但未完成证据读取；
- OCR/解析失败被误记为没有匹配；
- Verifier 无法重开原件或覆盖证明不一致。

可恢复失败必须告诉用户：失败阶段、已覆盖范围、未覆盖范围、是否有可复用中间索引，以及
“重试、修改目标、重新上传”中真实可执行的下一步。

## 7. 验收矩阵

实现阶段至少先写以下 Interface 级失败用例，再实现：

1. 109 页扫描 PDF，目标只存在第 1 个单据：完成首个对象和跨页边界验证后停止，不对其余页
   做高质量 OCR；
2. 同一文件目标散落第 2、57、108 页，问“查找 XXX 的数据”：三处全部返回，发现覆盖
   109/109，不能在第 2 页早停；
3. 问“查找第一个 XXX”：只返回顺序上的首个完整对象，并提供边界证明；
4. 第 40 页轻量发现超时：不得把它记为无匹配，任务必须补读或失败关闭；
5. 数字/扫描混合 PDF：数字页不做不必要 OCR，扫描候选页仍能产生坐标证据；
6. 同一用户换问法：复用发现索引，结果语义按新覆盖契约重新验证；
7. 不同用户上传相同 SHA-256：缓存和证据不可跨 Owner 访问；
8. 刷新任务页面：恢复真实发现/精读进度，不显示虚假的 `0/8 尚未开始`；
9. 发现索引命中文本但权威 OCR 不支持：不得发布该结果项；
10. 整源任务：全部页面完成权威读取，不允许 Pi 自行提前结束；
11. 相同完整性意图使用不同问法：Pi 生成等价覆盖契约，而不是依赖固定关键词；
12. 同一关键词处在“找一个示例”和“列出全部记录”的不同上下文：Pi 生成不同契约，
    确定性校验器不得覆盖其业务理解；
13. 明确指定某页：Pi 可以直接权威读取该页，不强制先执行全文件发现；
14. Pi 在覆盖账本仍有未知页面时提议完成全部匹配：Verifier 拒绝并返回结构化缺口，Pi
    随后扩大读取或进入可操作失败。

风险相称的验证证据包括：Interface 单元测试、API/事件集成测试、真实 109 页扫描 PDF A/B、
候选与覆盖 Verifier 回放、前端刷新/断线 Playwright，以及缓存所有权测试。不能用假 Provider
测试代替真实 OCR 的完备性与耗时证据。

## 8. 对当前试验实现的处理

当前工作区的 `PiSourcePreparer` 和整份 `.mangrove-ocr.jsonl` 属于问题复现后的试验实现，
不是本规格认可的最终 Interface。实现阶段应：

1. 保留可复用的页型判断、按页解析、版本化缓存和 Owner 隔离逻辑；
2. 把它们收进文档检索 Module 的 Implementation；
3. 移除“Pi 启动前必须生成整份高质量 OCR sidecar”的固定顺序；
4. 用覆盖契约驱动的 Interface 测试替换依赖 `prepare()` 调用顺序的试验测试；
5. 同步修复后台 `observe` 与前端 `inspect` 阶段词表不一致造成的虚假未开始状态。

禁止在旧前置预处理上继续增加按问法分支；那会重新形成场景路由，而不是来源驱动的深 Module。

## 9. 本轮保持不变的边界

- 不新增外部模型、OCR Provider 或自动外发；
- 不处理实时视频流或服务器容量；
- 不切换 Legacy/vNext 默认入口；
- 不创建版本、标签、提交或推送；
- 不把工程验证表述为用户实际操作验收或整个 Phase 4 完成。
