## 0. 路线图目标

下一阶段不以继续增加能力数量为首要目标，而是把现有工程能力收敛成一套：

1. 普通用户从统一入口即可稳定完成正式 Delivery；
2. 默认运行时、权限、外发和回滚行为与已接受 ADR 一致；
3. Secret、依赖、数据库迁移和主分支具备生产级安全门；
4. 文件、网页、HTTP 和数据库来源逐步共享同一任务与交付语义；
5. 达到真实部署条件后，再进入目标服务器、多节点和远程能力扩展。

完成 P0 后，项目应从“工程能力已完成”进入“可持续迭代的产品基线”；完成 P1 后，
项目应形成面向普通用户的统一主流程；P2 只在明确业务或部署条件满足后启动。

## 2. 执行原则与授权边界

### 2.1 固定执行原则

- 按依赖门推进：前一门的实现、定向测试、工程门、双轴审查和必要验收未通过，
  不进入下一门。
- 每项任务先建立可失败的测试或探针，再做最小实现，不进行相邻重构。
- 测试通过只代表工程证据；真实用户验收、Provider 资格、服务器资格和发布资格分别记录。
- 失败、超时、取消、状态不确定和权限不足默认失败关闭，不得把中间结果冒充 Delivery。
- 外部调用发生后结果不确定时，不自动重试；前端向用户展示状态和可理解的选择。
- 所有数据库迁移必须先备份、校验、执行、重放验证，并提供恢复证据。
- 历史任务、Legacy Delivery 和用户持有数据不得因默认运行时切换而迁移或改写。

### 2.2 不随本路线图自动授权的操作

本路线图不自动授权以下操作：

- 创建、修改或关闭 GitHub Issue/PR；
- 创建分支、提交、推送、合并、打标签或发布 Release；
- 修改 GitHub 分支保护、Ruleset、Secret 或其他远端配置；
- 使用真实业务数据调用外部 Provider；
- 使用、轮换、销毁或输出生产 Secret；
- 生产数据库迁移、部署、停机或其他不可逆操作。

实施到对应门时，必须说明精确范围、目标环境、外发内容和恢复办法，再取得所需授权。

## 4. P0：产品真实性与生产安全基线

### P0-01 vNext 默认链路与真实普通用户闭环

**目标**

消除“运行态是 `vnext_default`，主界面却显式提交 `legacy`”的产品不一致，证明普通用户
无需理解内部运行时即可完成一次正式 vNext Delivery。

**实现范围**

1. 前端运行时选择改为“平台默认 / 显式 Pi / 显式 Legacy”语义；用户未覆盖时不发送
   `runtime_version`。
2. API 请求模型不再用容易误导客户端的 Legacy 默认值；服务端 Rollout 始终是默认决策权威。
3. 界面显示任务最终采用的运行时，并保留显式 Legacy 入口。
4. 保持 P0 自动回退：阻断后新任务默认 Legacy，显式 Pi 失败关闭；恢复不得自动发生。
5. 默认使用外部 Provider 时，继续展示外发范围、连接身份和结果不确定状态；不得增加盲重试。

**验证与完成标准**

- 单元/契约测试覆盖：字段省略、显式 Pi、显式 Legacy、P0 阻断、恢复和 Owner 隔离。
- 浏览器 E2E 覆盖主工作台默认创建任务，确认 RuntimeAssignment 持久化为 Pi。
- 显式 Legacy 仍可工作，历史任务和既有 Delivery 零改写。
- 在明确外发范围并取得对应授权后，使用纯合成数据完成：上传 → Pi → Candidate →
  独立 Verifier → Delivery → 预览/下载。
- 记录 Provider Usage、取消/超时语义和数据库零异常证据。
- 双轴审查无阻断问题，用户验收通过。

**明确不做**

- 不删除 Legacy。
- 不扩大 Provider、数据类型或普通用户能力市场受众。
- 不因本任务重构整个 Semantic Workspace。

### P0-04A 最小 CI 工程门

**目标**

把现有测试和构建能力变成每次变更都可重复执行的自动门，而不是依赖人工记忆。

**实现范围**

1. 后端 Python 3.13 快速单元/契约测试。
2. 前端安装、类型检查和正式构建。
3. 依赖一致性、Secret 扫描、迁移 dry-run 和 UTF-8 检查。
4. Docker、完整回归、真实 Provider 和 G1 冻结集放入手动或定时重门，避免 PR 使用生产 Secret。
5. 保存结构化测试摘要和失败日志，不保存用户数据或 Secret。

**完成标准**

- 干净环境可重复运行；失败步骤返回非零状态。
- 缓存不影响正确性，端口和子进程得到验证与清理。
- 文档说明快速门、完整门、人工门分别证明什么。
- CI 文件完成工程验证；GitHub 远端强制规则留到 P0-04B 独立授权。

### P0-05 显式数据库迁移体系

**目标**

统一数据库演进方式，停止由应用启动过程静默执行不可追踪的 DDL 和数据回填。

**实现范围**

1. 建立编号迁移注册表、当前版本表和确定性执行顺序。
2. 把现有启动时建表、ALTER 和回填逐步移到显式迁移。
3. 支持 dry-run、备份路径、备份 SHA、完整性检查、幂等重放和恢复验证。
4. 应用启动只验证 Schema；版本不兼容时失败关闭并给出可执行提示。
5. 评估并验证 `foreign_keys`、`busy_timeout` 和 WAL；不得未经并发/恢复测试直接启用。

**完成标准**

- 空库、当前生产库副本、重复执行和中途失败场景全部通过。
- 既有表和历史业务数据零意外改写。
- 迁移锁能阻止并发迁移；恢复副本可正常启动和读取。
- 所有后续数据结构变更只有一条权威迁移路径。

### P0-02 Secret 存储统一

**目标**

让配置中心与模型连接共享同一 Vault/SecretRef 安全边界，消除明文 Secret 数据库存储。

**实现范围**

1. 盘点所有 `secret=True` 配置项及其读取者、写入者和备份路径。
2. 原始 Secret 只写入现有 Vault，业务表仅保存不透明 SecretRef 和必要元数据。
3. 使用 P0-05 迁移体系转换旧值；迁移失败时保留旧库并失败关闭。
4. API、日志、审计、导出、异常和诊断报告统一脱敏。
5. 扫描受控备份是否含旧明文；是否轮换或销毁 Secret 必须另行授权。

**完成标准**

- 新写入和更新不产生明文数据库记录。
- 当前库迁移副本与新备份通过脱敏扫描。
- Vault 不可用、SecretRef 无效、跨 Owner 和权限不足场景全部失败关闭。
- 正常 Provider、SMTP/通知、数据库连接等读取路径有回归证据。

### P0-03 依赖拆分与漏洞治理

**目标**

减小生产镜像、依赖冲突和供应链攻击面，并对 GitHub 告警给出可验证处置。

**实现范围**

1. 建立导入与运行可达性清单，确认 MLflow、Streamlit、Flask、Databricks、GPU 包等是否需要。
2. 优先移除未使用且触发 Critical 告警的依赖。
3. 拆分 runtime、dev/test、GPU、evaluation 和可选采集依赖。
4. 在干净环境生成受控锁定结果，解决 `pip check` 冲突。
5. 对剩余告警记录：受影响组件、可达路径、当前缓解、升级计划和残余风险。

**完成标准**

- 生产镜像只安装实际运行所需依赖。
- `pip check` 通过，前后端构建和完整核心回归通过。
- Critical/High 告警已修复，或有经审查的不可达证据和时限明确的风险记录。
- GPU、评测和开发环境仍有可重复安装入口。

### P0-04B 主分支保护落地

**目标**

把已经稳定运行的 CI 检查设为 `main` 的远端合并门。

**完成标准**

- 现场重新核对远端、默认分支和仓库权限。
- 在取得独立授权后配置必要检查、禁止强推和审查要求。
- 用测试 PR 验证失败会阻止合并、成功可以正常通过。
- 记录紧急修复流程，但不设置可以静默绕过审计的后门。

### P0-06 当前状态与交接收口

**目标**

让新会话或新维护者只读当前权威入口即可得到准确的下一步，不再被已关闭 Issue 和旧分支误导。

**实现范围与完成标准**

- `handoff.md` 只保留当前分支、现场状态、在制任务、下一门禁和授权边界。
- `docs/status/current.md` 保留当前能力矩阵，把长历史移到明确的历史索引或既有报告。
- README、AGENTS 和状态台账中“尚未完成”的描述与现场证据一致。
- 历史执行报告不改写结论；必要时只从当前台账引用其证据。
- 记录 P0 完成证据、未完成事项、风险和 P1 第一项的精确开工条件。

## 5. P1：统一产品主流程

### P1-01 统一 Source → TaskRevision → Delivery

**目标**：把文件、Conductor 网页采集、HTTP 和数据库来源收敛为来源适配器，统一进入
TaskRevision、执行、验证和正式 Delivery；Legacy 在迁移完成前继续只读/兼容。

**关注点**

- 先写产品流程、领域契约和迁移 ADR，再做代码。
- 来源快照、连接版本、Owner、外发确认和能力 digest 必须冻结。
- Conductor 输出不得绕过正式 Delivery 语义。
- 采用纵切片：先网页来源，再 HTTP，最后数据库；每片独立验收。

**工作量**：3～6 周。

### P1-02 深化 Semantic Workspace 模块

**目标**：形成窄而稳定的任务生命周期接口，降低路由、Store、Worker 和执行器之间的耦合。

**关注点**

- 路由只做 HTTP 映射；生命周期模块负责创建、修订、取消、重试和发布。
- Repository 提供聚合级事务，不继续扩大底层 Store 公共方法面。
- 消除跨路由私有函数依赖。
- 前端把任务状态机、请求副作用和展示组件拆成可单元测试接缝。
- 每次只迁移一个真实流程，不做全量重写。

**工作量**：3～5 周，可与 P1-01 按纵切片合并执行。

### P1-03 生产可观测性与认证加固

**目标**：让远程多人使用时的问题可发现、可定位、可审计、可恢复。

**关注点**

- 结构化日志、请求/任务关联 ID、指标、SLO 和告警。
- 任务成功率、Delivery 耗时、修复次数、Provider 延迟/失败/成本等业务指标。
- 登录限流、密码策略、短期访问 Token、刷新与撤销、TLS/CSP。
- Readiness 与业务健康分层，不因外部 Provider 短暂异常让 API 整体失效。

**工作量**：2～3 周。

### P1-04 普通用户安全开放平台能力

**目标**：在不削弱现有治理门的前提下，让普通用户按受众和配额使用已验证的平台能力。

**关注点**

- 受众、配额、成本提示、外发确认和审计 UX。
- 分批开放、可回滚、跨 Owner 拒绝和撤销后新任务失败关闭。
- `admin_gray` 资格不自动等于 `users` 受众资格。

**工作量**：2～4 周。

### P1-05 前端测试与性能治理

**目标**：补充快速组件反馈，降低大型 E2E 和首屏包体带来的维护成本。

**关注点**

- 增加 Vitest/组件测试，覆盖状态机、表单、权限、超时和结果不确定提示。
- PDF、编辑器和大型页面按需加载。
- 建立包体预算、关键页面性能基线和无障碍检查。

**工作量**：1～2 周。

## 6. P2：条件型扩展

| 方向 | 启动条件 | 首轮范围 | 预估 |
|---|---|---|---:|
| G5 真实 Linux/GPU 服务器验收 | 已取得目标服务器、部署网络和资源预算 | Compose、路径、并发、故障恢复、备份恢复、容量与 7～14 天观察 | 3～5 个工作日 + 观察期 |
| 远程 MCP/Registry/SecretRef | 有明确远程能力交付对象和信任边界 | 协议、身份、SecretRef、供应链、取消/超时和审计 | 4～8 周 |
| Phase 4C 多媒体 | 有真实业务场景、样本集和正式输出定义 | 先单一媒体纵切面，不同时铺开音视频图像 | 3～6 周 |
| 多节点/分布式队列 | 单机出现持续写锁、恢复或吞吐瓶颈 | 分布式租约、队列恢复、幂等和任务归属 | 4～8 周 |
| 对象存储/PostgreSQL | 数据量、并发或多实例达到量化阈值 | 先迁移契约和恢复演练，再切生产 | 4～8 周 |
| SQLite/TSV 正式输出 | 有明确用户需求和验收样例 | Renderer、QA、预览、下载和格式契约 | 每项 2～5 人日 |

建议扩容触发阈值：需要两个以上应用实例、持续出现 SQLite 写竞争、任务必须跨进程恢复、
数据库持续增长到数百 MB，或长期存在 10～20 个以上并发执行任务。没有达到触发条件时，
不为技术预期提前引入分布式复杂度。

## 7. 每项任务的标准执行模板

每项任务依次执行以下门：

1. **现场重验**：读取 handoff/current/CONTEXT/ADR，核对 Git、WIP、运行态、数据库和远端。
2. **冻结工单**：写清 Scope、非 Scope、依赖、风险、外发范围、DoD 和授权门；是否发布为
   GitHub Issue 另行确认。
3. **测试先行**：建立可变红的单元、契约、集成或浏览器探针。
4. **最小实现**：只修改完成目标所需的接缝，不顺带重构。
5. **定向验证**：先运行受影响测试，再运行与风险相称的完整门。
6. **双轴审查**：Standards 审查工程规则，Spec 审查目标和 DoD。
7. **真实验收**：涉及 UI、Provider、数据库、Docker 或目标服务器时，分别留下现场证据。
8. **状态收口**：更新唯一当前台账和 handoff；提交、PR、合并、关闭 Issue、发布分别按授权执行。

每个任务必须区分以下证据等级：

- `IMPLEMENTED`：代码存在。
- `ENGINEERING_VERIFIED`：自动测试和工程探针通过。
- `LIVE_ACCEPTED`：真实入口、真实环境或真实 Provider 验收通过。
- `RELEASED`：经独立授权完成提交、合并、标签、Release 或部署。

低等级证据不得替代高等级结论。

## 8. 阶段完成定义

### P0 完成

- 普通用户从主入口默认获得 vNext，并完成至少一条正式 Delivery 验收。
- 显式 Legacy、P0 回滚和结果不确定处理保持正确。
- 配置中心 Secret 不再明文落库，新备份不含明文 Secret。
- 生产依赖最小化，Critical/High 告警完成修复或形成经审查的风险结论。
- CI 可重复运行；经授权后 `main` 受到必要远端保护。
- 数据库只通过显式、可备份和可恢复的迁移演进。
- current/handoff 与现场一致。

### P1 完成

- 文件、网页、HTTP 和数据库来源共享统一任务与 Delivery 语义。
- Semantic Workspace 的核心接口收窄，路由、生命周期、持久化和执行职责清晰。
- 普通用户能力开放有受众、配额、外发、审计和回滚闭环。
- 关键业务指标、日志、告警和认证安全满足远程多人使用要求。

### 路线图重新评审条件

出现以下任一情况时暂停后续门并重新评审：

- 新的 P0 安全、数据完整性、跨 Owner 或正式 Delivery 问题；
- 产品目标、角色、数据外发边界或默认运行时决策变化；
- 引入新的外部 Provider、远程 MCP、对象存储或数据库；
- 目标部署环境从单机变为多实例；
- 当前证据与 `docs/status/current.md`、代码或数据库实况冲突。
