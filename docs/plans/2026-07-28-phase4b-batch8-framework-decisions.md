> 记录日期：2026-07-28
>

> 顺序或授权。干净镜像、Linux 依赖、Docker 一键启停、并发、故障恢复和服务器验证，

## 1. 当前目标

下一阶段优先完成统一任务闭环和通用质量框架，不以逐项修复批次 7 的模型、页面和格式
细节为主。

统一任务闭环定义为：

```text
任务提交 → 理解需求 → 制订计划 → 读取来源 → 执行 → 验证 → 正式交付
```

批次 8 在该闭环之上补齐通用评测、可观测性和故障处理框架。

## 2. 已确认范围

### 2.1 输入来源

- 使用现有较成熟的 Word/PDF、Excel/CSV 能力完成端到端验收；
- 为网页、API 和数据库保留统一接入契约；
- 本阶段不要求网页、API 和数据库新来源真实跑通。

### 2.2 前端

前端只实施支撑主流程所必需的改动：

- 准确展示统一任务状态；
- 展示当前实际执行阶段；
- 展示真实、可操作的错误；
- 正确展示取消状态；
- 优先展示通过验证的正式结果。

本阶段不重做整体视觉，也不把文件预览等批次 7 体验细节纳入主要打磨范围。

### 2.3 复合来源任务

- 本阶段不实现同一任务同时消费文档和表格并生成合并结果的复合来源执行；
- 系统必须准确识别该能力尚未支持，向用户明确说明并安全停止；
- Word/PDF 文件集仍属于文档类来源，Excel/CSV 文件集仍属于表格类来源，不因文件数量
  增加而自动成为复合来源任务；
- 不得把只处理部分来源的结果冒充完整结果。

### 2.4 阶段拆分

原批次 8 拆分为两个独立阶段：

- **批次 8A：本机主流程与框架验收**。覆盖统一任务闭环、通用评测、可观测性、故障处理
  和必要的最小通用修复；
- **批次 8B：部署、压力与封板**。覆盖服务器 Compose、GPU 租约、10–20 用户压力门、
  部署验证和 Phase 4B 封板审计。

当前方案只覆盖批次 8A。批次 8B 必须再次获得用户确认后才能启动，且不得用 8A 的本机
结果宣称 Phase 4B 已封板。

### 2.5 真实闭环门

批次 8A 的退出门必须包含 DOCX、PDF、XLSX、CSV 各至少一个真实文件，并从用户提交开始
真实经过模型、后台执行、验证、正式交付、下载和重开校验。

Mock、单元测试和直接调用中间执行器只作为补充证据，不能替代真实用户闭环，也不能据此
宣称批次 8A 通过。

### 2.6 固定成功场景

批次 8A 至少固定以下四类公开脱敏真实文件场景：

| 输入 | 任务语义 | 正式输出 |
| --- | --- | --- |
| DOCX | 限定范围提取并汇总 | TXT |
| PDF | 证据绑定的条款提取或核查 | DOCX、PDF |
| XLSX | 筛选、保留指定列并排序 | XLSX |
| CSV | 去重或分组汇总 | CSV、JSON |

每个场景必须保存可机械比对的预期计划、结果内容、证据范围和正式产物校验要求。仓库已有的
公开脱敏夹具优先复用；不得把用户真实业务文件纳入自动化测试仓库。

### 2.7 固定失败场景

用户完整路径必须验证：

1. 信息不足时暂停，用户补充后从原任务继续；
2. 用户在执行期间取消，终止任务且不发布正式结果；
3. 复合来源任务明确说明暂不支持，不只处理部分来源；
4. 自然语言与界面输出格式冲突时暂停确认，不静默替换。

受控后端故障注入必须验证：

1. 模型超时或结构化输出截断后有界停止；
2. 转换工具崩溃或正式产物损坏时拒绝发布；
3. 同一任务重复投递时不重复执行或重复发布；
4. 跨用户访问任务、事件和下载均被拒绝。

所有失败路径都必须安全停止、保留可追溯诊断、展示真实且可操作的状态，并确保正式交付
数量为零。故障注入只能作用于测试隔离环境，不得破坏用户运行数据。

### 2.8 任务轨迹的数据边界

可观测系统保存完整过程元数据，包括任务与阶段身份、原文件 ID/哈希、模型与工具版本、
耗时、重试、错误、证据位置、正式结果 ID/哈希。

业务原文和正式结果继续由现有不可变制品及交付存储保存。任务轨迹不得重复保存原文、
完整提示内容或正式结果正文，也不得成为第二套业务数据仓库。

### 2.9 本地模型与上下文预算

批次 8A 采用本地分阶段策略，不要求一次模型调用读取整份来源：

- 计划编译只接收用户要求、来源结构和必要摘要，不接收整份文档正文；
- 结构化编译关闭思考模式，使用紧凑 Schema 和显式输入/输出预算；
- 长内容按章节或元素分批处理，并用覆盖账本证明全部目标均已扫描；
- 调用前预估输入与输出预算，预计超限时先分块，不等待截断后重复空转；
- 安全且唯一可推导的计划字段允许确定性补齐；涉及用户语义的缺口必须暂停询问；
- 不同阶段可以使用不同的本地模型或同一模型的不同配置；
- 禁止失败后静默切换到外部 API。

本次真实失败已确认的直接表现是结构化编译输出达到 `max_tokens` 上限并被截断，不能在
缺少证据时把它概括为“原文超过上下文窗口”。

### 2.10 用户失败说明

普通用户看到的失败信息至少包含：

1. 失败阶段；
2. 可理解的直接原因；
3. 尝试次数和总耗时；
4. 是否读取过来源、是否生成过中间结果；
5. 是否产生或发布正式文件；
6. 可执行的下一步和稳定错误编号。

管理员/开发者可以额外查看模型参数、Token 使用、逐次原始诊断、后台任务身份和错误指纹
等技术元数据。普通用户说明不得退化为“任务失败”“未知错误”或只要求联系管理员，也不得
泄露堆栈、内部路径、完整提示内容、业务正文或其他用户信息。

### 2.11 任务档案与角色可见性

现有任务数据库、事件记录、Manifest、制品及其哈希继续组成长期生产档案和权威溯源记录。
OpenTelemetry/Phoenix 等观测数据只作为辅助诊断，不得成为唯一业务证据；诊断数据清理或
更换工具不得破坏任务历史。

- 普通用户可以查看自己任务的要求、来源、输出格式、阶段、尝试与耗时、失败说明、交付、
  版本和证据位置；
- 管理员/开发者在获得相应诊断权限后，可以额外查看模型配置、Token、Worker、错误指纹、
  内部阶段耗时和技术堆栈；
- 管理员诊断默认只展示技术元数据，不因管理员身份自动展开用户业务正文；
- 其他普通用户不得查看该任务、文件、事件、诊断或下载；
- 管理员跨用户正文治理不在批次 8A 内扩建。

### 2.12 开源工具组合

批次 8A 采用最小增量的成熟开源工具组合：

- 复用 `pytest + Hypothesis`，覆盖契约、状态机不变量、权限、幂等、格式协商和确定性
  故障注入；
- 复用 Playwright，保留快速 Mock UI 门并增加串行真实后端、真实模型、真实文件、真实下载
  的 PC 闭环；
- 复用现有 OpenTelemetry 依赖，只增加统一任务七阶段的必要业务 span；
- 新增固定版本 Phoenix Docker，作为可选本地管理员诊断后端，不安装进主 Python 环境；
- 新增固定版本 Promptfoo 隔离 PoC，先覆盖六个案例，稳定后再决定是否升级为正式门禁；
- 继续复用 Testcontainers；Toxiproxy 暂不引入，只有确定性测试无法覆盖真实 TCP 风险时
  再评估。

开工前必须先处理依赖事实漂移：当前本机 OpenTelemetry/Traceloop 实际版本与
`requirements.txt` 声明不一致。应在隔离验证后选择重装锁定版本或有意更新锁文件，不能
直接在两套版本事实之间验收。

选型证据见
[`2026-07-28-phase4b-batch8-open-source-tooling.md`](../research/2026-07-28-phase4b-batch8-open-source-tooling.md)。

### 2.13 双重完成标准与用户验收说明

批次 8A 采用两个不得混淆的状态：

- **工程验证通过**：全部自动化门禁和四类真实文件闭环通过；
- **用户验收通过**：用户亲自复验至少一个 DOCX → TXT 任务和一个表格任务，并明确确认。

用户确认前，不得宣称“用户验收通过”，不得进入批次 8B，也不得封板。

批次 8A 必须在工程验证完成后交付一份面向用户本人的简明验收清单，不扩写为通用产品
手册。该清单至少包含：

- 验收前环境检查；
- 使用的公开脱敏测试文件及其身份；
- 可直接复制的任务要求；
- 页面逐步操作，用户正常验收时不需要操作命令行或读取后台日志；
- 每一步应看到的状态；
- 下载、重开和内容核对方法；
- 通过/失败判定；
- 发现问题时需要记录的任务编号、错误编号和截图位置。

### 2.14 工作台清理后的精简审计记录

当前代码会在回收站 30 天到期后清理工作台任务、revision 和事件聚合记录。批次 8A 调整为：

- 普通用户工作台仍在 30 天后移除相应任务，且任务不能恢复；
- 单独永久保留一条精简审计记录，含任务/所有者身份、要求哈希或脱敏摘要、来源和结果
  身份及哈希、请求格式、终态、稳定错误编号、关键时间和清理原因；
- 精简审计记录不保存完整要求、文件名、业务正文、证据文本、模型回复、凭证、本机路径或
  下载链接；
- 工作台永久删除不得删除精简审计记录；未来物理擦除需单独的数据治理授权。

架构决策见
[`ADR-0015`](../adr/0015-workspace-audit-tombstone.md)。

## 4. 术语

- **主流程**：从任务提交到正式交付的完整用户路径。
- **框架**：被不同任务类型复用的状态、契约、执行、验证、观测和故障处理机制。
- **细节打磨**：不阻断闭环的视觉、交互、模型提示和单场景质量优化。
- **正式结果**：通过 QA、完整性和权限校验并发布的交付产物，不包括中间计划或临时结果。

## 5. 批次 8B 已确认决策

### 5.1 阶段拆分

批次 8B 拆分为两个独立阶段：

- **8B-1 服务器就绪包**：在开发机完成当前 Phase 4B 可真实验证的编排、检查、并发、
  故障、恢复和验收资产，不生成容易随后续工程漂移的最终服务器制品；
- **8B-2 实机验收**：在目标服务器上验证驱动、容器、GPU、存储、10–20 用户并发、
  长期运行和故障恢复能力。

8B-1 完成后可以继续后续功能阶段，但 Phase 4B 保持未封板。目标服务器准备和 8B-2
均安排在整个工程功能开发完成后的最后阶段；服务器未就绪前，不得用本机、Mock 或脚本
验证结果替代实机验收，也不得宣称服务器部署完成或 Phase 4B 已封板。

### 5.2 8B-1 完成标准

8B-1 不接受只有说明文档或不可运行的脚本骨架。服务器就绪包必须能在当前开发机实际
运行并验证至少以下入口：

- Compose 配置解析与 profile 校验；
- 前置条件检查工具逻辑和“本机可验证/待实机验证”分类；
- 服务启动后的统一健康检查；
- 可重复执行的压力测试入口；
- 只作用于隔离测试环境的故障注入入口；
- 区分本机结果和待补实机结果的验收报告模板。

GPU、RAID、10–20 用户真实并发、长期运行和恢复数据只能在 8B-2 填写。本机无法验证的
项目必须明确标记为“待实机验收”，不能以 skip 或 Mock 结果记为通过。

### 5.3 基础设施范围

8B-1 只编排当前已经实现并能在开发机验证的服务，不提前实现 Phase 5B，也不创建空的
Compose profile、未使用的环境变量或伪健康检查。本阶段只记录后续集成点，不实施：

- SQLite 到 PostgreSQL 的生产迁移；
- RabbitMQ/Celery 多实例分布式队列；
- Redis 锁、租约和短状态服务；
- 真正的多 GPU 租约与调度。

这些能力继续由各自后续阶段开发和验证；有真实服务时再增加对应 profile。不得为了让
服务器蓝图看起来完整而在 8B-1 引入未经规格确认的生产化重构或空壳配置。

### 5.4 业务覆盖范围

8B-1 只覆盖 Phase 4B 统一任务闭环及其必需依赖：

- Mangrove 前端与 FastAPI；
- 当前工作台后台 Worker；
- 语义编译、来源检查、绑定、执行、验证和正式交付；
- 当前已经接入的本地/LAN 模型与文档解析服务；
- Phoenix 低敏观测入口。

聊天、全网采集、MediaCrawler、SearXNG、Firecrawl 及其他业务链不纳入本批验收。
当前只在文档中记录顶层组合边界，不预建其他业务链的空 profile。等相应工程阶段完成后，
再把真实服务纳入最终服务器编排。

### 5.5 本机并发门

8B-1 使用 10–20 个虚拟用户运行轻量并发场景，但只把以下项目作为通过条件：

- 不发生跨用户任务、事件、诊断或下载泄露；
- 相同任务不重复执行或重复发布正式交付；
- 取消、失败和完成状态符合生命周期契约；
- 不出现无限重试或同失败空转；
- 受测服务不会直接崩溃。

本机延迟、吞吐和资源使用只记录为开发环境基线，不设生产性能达标线。p95 延迟、GPU
吞吐、容量上限和长期稳定性只能在 8B-2 实机验收中形成结论。

### 5.6 故障注入安全边界

8B-1 只允许在隔离测试环境中执行可恢复、非破坏性的故障注入，包括终止专用测试
Worker/转换容器、模拟模型超时或连接中断、停止 Phoenix，以及通过受限测试卷或故障
适配器模拟磁盘不足。

故障门必须验证重启、幂等恢复、错误说明和损坏产物拒绝发布。禁止填满宿主机磁盘、删除
真实任务数据、终止用户正在使用的容器、修改 Docker Desktop 全局配置，或把故障扩散到
非测试服务。

### 5.7 测试数据隔离

8B-1 的并发、故障和恢复测试只使用仓库中的公开脱敏夹具，并使用独立的测试用户、
测试数据库、ArtifactStore 和下载目录。测试不得读取现有用户任务，不得把真实业务文件
复制进压测目录、Compose 镜像或测试制品。

8B-2 如需使用真实业务样本，必须另行确认样本存放位置、脱敏规则、访问权限和销毁方式。

### 5.8 目标操作系统

8B-1 使用可移植的 Linux 容器契约，当前 Windows + Docker Desktop 只负责验证 Compose、
服务契约和可在开发机运行的操作入口，不作为任何服务器操作系统兼容性证据。

Ubuntu Server 24.04 LTS 只是 8B-2 的首选候选，不在 8B-1 冻结。最终选择 24.04
还是回退 22.04，必须由目标 L20 服务器上的 NVIDIA 驱动、CUDA、Container Toolkit、
vLLM 和文档解析服务实机矩阵决定；当前不维护两套主配置或提前编写系统专属安装流程。

### 5.9 网络访问边界

8B-1 保留 Mangrove 在可信局域网内供多台 PC 访问的现有使用方式。前端和业务 API
可以监听当前开发机的局域网接口，并完成一次其他 PC 的真实访问验证。

Phoenix、指标、内部健康检查和其他管理端口默认只允许服务器本机或管理员网段访问，
不得向所有普通局域网用户开放。8B-1 只记录未来防火墙意图，不提前生成或应用目标
服务器专属规则，也不配置路由器端口转发、公网地址、真实域名或公网证书；这些工作留到
最终实机阶段另行确认。

### 5.10 备份与恢复

8B-1 必须在隔离测试数据上完成可重复的备份与恢复闭环，覆盖当前 SQLite 任务库、
ArtifactStore、正式交付、Manifest 和恢复所需配置。备份包必须带版本、文件清单和哈希；
恢复必须写入全新的测试目录，并重新验证任务所有权、历史结果、证据关联和授权下载。

备份失败、文件缺失或哈希不一致必须明确失败，不能生成看似成功的不完整备份。RAID、
异机/离线备份和真实灾难恢复演练继续留给 8B-2。

### 5.11 用户验收方式

8B-1 提供当前开发机可实际运行的 PowerShell 一键验收入口，自动检查 Compose、镜像、
端口、健康状态、测试数据隔离、本机并发门、故障恢复和备份恢复，并生成中文
Markdown/HTML 验收报告。可复用的 Bash 入口只在当前环境能够真实运行和验证时交付；
否则留到 8B-2，不用未执行脚本冒充 Linux 验收。报告必须明确区分“已通过”“失败”和
“待 8B-2 实机验证”。

用户只需额外从另一台局域网 PC 完成一次登录、任务提交和正式结果下载。正常验收不要求
用户阅读 Docker 日志或手动拼接多条诊断命令；失败报告必须提供稳定检查编号和下一步。

### 5.12 延后最终服务器制品

以下内容依赖尚未准备的目标服务器，或会随后续工程变化而快速过期，统一留到 8B-2：

- 最终全工程 Compose 和全部镜像集合；
- 离线镜像归档及导入/导出流程；
- Ubuntu 版本、驱动、CUDA 和 GPU 运行时冻结；
- 真实域名、TLS、公网入口和目标服务器防火墙规则；
- RAID、异机/离线备份和真实灾难恢复；
- 生产性能阈值、长期运行结论和容量上限。

8B-1 只固定当前实际使用镜像的版本事实，不生成巨型离线包。目标服务器就绪后先核对
网络条件；只有不能联网时，才在 8B-2 生成带清单和哈希的离线部署包。

### 5.13 验收环境隔离

8B-1 使用独立的 Compose 项目名、测试用户、测试目录、数据库、ArtifactStore 和必要的
独立端口。启动、故障注入、恢复和清理流程不得停止、覆盖、迁移或删除当前正在使用的
Mangrove、Phoenix、现有任务数据及其他开发服务。

验收结束时只允许清理本批创建且身份可机械确认的测试容器、网络、卷和临时文件；目标
不明确时必须停止，禁止用全局 Docker 清理命令代替定向清理。

### 5.14 Docker Desktop 执行方式

8B-1 使用当前 Windows 开发机上的 Docker Desktop 构建并运行最新版 Mangrove，不另外
搭建 Linux 服务器或虚拟机。新增面向当前 React + FastAPI + Phase 4B 工作台的独立
Compose，不直接覆盖仓库中仍指向旧 Streamlit/WebSocket 程序的历史 Docker 配置。

新 Compose 必须与当前运行环境隔离，并在 Docker Desktop 中真实完成页面、任务、交付、
下载和局域网访问验证。最终服务器阶段再评估如何复用同一套 Linux 容器契约。

`start_all.bat` 和 `stop_all.bat` 纳入 8B-1 同步改造范围，统一默认使用 Docker
Desktop 启停当前完整开发环境。

### 5.15 统一一键启停

`start_all.bat` 不再区分宿主机模式和 Docker 参数模式。默认一次检查 Docker Desktop，
并启动最新版 Mangrove 前端、FastAPI、当前工作台 Worker、Phoenix，以及现有
SearXNG、Firecrawl、RSSHub；健康检查完成后统一显示访问地址。用户不需要再执行第二条
启动命令。

`stop_all.bat` 一次定向停止上述同一组 Mangrove 资源，不再按 8088/5173 端口强制结束
身份不明的进程，也不得执行全局 Docker 清理。SearXNG、Firecrawl 和 RSSHub 虽随整套
开发环境启停，但其业务能力仍不计入 8B-1 的 Phase 4B 验收范围。

### 5.16 Docker 开发热更新与干净镜像门

日常 `start_all.bat` 启动支持源码挂载和热更新的 Docker 开发环境：前端修改后自动刷新，
后端修改后自动重载，不要求用户每次改代码都重新构建镜像。

8B-1 一键验收必须自动构建一份不挂载宿主源码的干净镜像，并在隔离项目、目录和端口上
验证当前 Phase 4B 闭环。开发热更新环境通过不能替代干净镜像门，相关构建、启动和清理
均由验收脚本完成，不增加用户日常启停步骤。

### 5.17 分级健康策略

一键启动将服务分为两级：

- **核心服务**：前端、FastAPI、工作台 Worker、任务库和制品存储。任一核心服务启动或
  健康检查失败时，`start_all.bat` 必须明确返回整体启动失败；
- **辅助服务**：Phoenix、SearXNG、Firecrawl、RSSHub。单个辅助服务失败时 Mangrove
  可以继续运行，但启动摘要必须显示“部分能力不可用”、具体服务和下一步。

本地模型或 LAN 解析服务不可达时，页面仍可打开，但依赖它们的任务能力必须标记为不可用，
且 8B-1 完整验收不得通过。任何降级都不能显示成“全部服务正常”。

### 5.18 启停与数据保留

`stop_all.bat` 只定向停止 Mangrove 管理的容器，始终保留数据库、上传原件、任务结果、
Phoenix 数据和其他持久卷。日常重建镜像也不得清理这些数据。

启停脚本禁止使用 `docker compose down -v`、全局 Docker prune、按端口杀死身份不明
进程或删除宿主数据目录。未来如需重置测试环境，必须使用独立入口，先解析并展示精确
目标，再取得用户确认；重置能力不得隐藏在 `stop_all.bat` 中。

### 5.19 Docker Desktop 自动就绪

`start_all.bat` 发现 Docker Engine 不可用时，先尝试启动本机已安装的 Docker Desktop，
并在明确超时内等待 Engine 就绪，再启动 Mangrove。Docker Desktop 未安装、启动失败或
超时必须显示可理解的原因和处理办法，不能无限等待，也不要求用户先手动打开 Docker
Desktop 再运行脚本。

### 5.20 现有资料与配置复用

日常 Docker 环境继续使用现有用户账号、任务数据库、上传原件、历史结果和当前配置。
这些资料只能通过受控挂载或外部配置传入容器，不得复制进镜像或提交 Git。

首次切换前必须完成只读检查和可恢复备份；8B-1 不迁移、不改写、不删除现有数据。自动
验收环境继续使用完全独立的测试数据库、ArtifactStore、用户和端口，不能污染日常资料。
