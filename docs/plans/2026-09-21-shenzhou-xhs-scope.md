# 神州小红书银行权益场景：当前阶段方案

日期：2026-09-21。状态：用户已明确“确认”，授权按本方案进入 V3 业务实现。本文保留已确认的范围与验收标准；当前实现与验证状态以 `../status/current.md` 为准。

## 1. 已确认的目标与边界

- V3 是 V2 的独立完整副本。用户进一步明确产品定位：V3 相对 V2 只增加“神州银行权益”专属应用场景，其他能力和使用方式基本保持不变；不足的能力在现有模块中补齐，不按新平台建设。
- 用户确认后已进入 V3 本地实现及离线工程验证。真实小红书、模型和 OCR 联调、切换运行服务、服务器部署、提交及发布单独核验，不从方案确认推断这些操作已经完成。
- 本轮用户明确确认的业务口径优先；Excel 是字段范围依据，HTML 补充业务规则，截图是解释规则和设计验收的样例。附件中的代跑、巡检、上线日期等不构成当前执行指令。
- 覆盖 Excel 全部“纳入／尽量纳入”项，再划分本期必做、有条件支持、可后置；不是只看 P0。
- 支持内部代跑和神州用户自助操作；同时交付人工核对用 Excel 与结构化 JSON／接口。
- 已确认使用权限与入口：V3 所有已登录用户均可使用该场景，沿用既有权限，不增加场景专属授权；用户直接用自然语言提出需求，平台识别后套用场景规则，不要求先选择模板。
- 已确认来源选择：用户未指定来源时沿用 Mangrove 的通用来源选择逻辑，不因内容涉及银行权益就默认小红书；用户明确要求小红书时，才使用对应的专属采集规则。
- 已确认默认处理深度：用户明确要求采集小红书银行权益，即使没有另说 OCR 或字段抽取，也默认识别图片并整理权益字段，同时保留原始内容与证据。用户明确限制只取原始内容等处理范围时，仍遵循其本次指令；场景默认行为不能覆盖 query。
- 已确认默认客群：未指定客群时覆盖该银行各类零售客群，结果分别标明；明确指定时才定向筛选。未指定不等于来源客群未知，不能因未指定目标而标记客群不符，来源属性缺失时仍须标明未知。
- 已确认默认信用卡边界：未进一步指定的银行权益任务默认排除纯信用卡权益帖，混合帖保留并区分；用户明确要求信用卡时纳入。此项仅为缺省范围，不能覆盖用户 query 中明确的主题或客群要求。
- 已确认交付流程：先提供可下载初稿，由用户核对并确认后才进入正式交付；沿用 Mangrove 现有流程。人工确认是必要条件，不替代正式发布所需的完整性与 QA 条件；不能在初稿完成后擅自继续后续核对或发布。
- 使用环境为维护者本机及华苏公网服务器，最多 10 人同时提交采集任务，没有截止日期。
- 沿用已有 Cookie 配置：用户个人设置优先，未配置时使用平台配置。凭证失效不等于用户授权切换另一账号。
- 补充确认的采集规则：平台自动初筛；首批 20 条候选，不足时自动补搜，累计最多检索 100 条候选；图片识别后不符合时间／客群要求的帖子自动递补；累计最多对 20 篇帖子的全部图片做 OCR，得到 5 篇符合要求的帖子后提前停止。达到上限仍不足时交付实际结果和不足原因，不突破上限。
- 已确认多银行额度：上述初始数量、目标数量和累计上限均按每家银行独立计算。多银行任务中，每家分别争取 5 篇结果、最多检索 100 条候选、OCR 最多 20 篇，不共用额度；一家达到停止条件不影响其他银行继续完成。任务执行记录需分别展示各银行的数量和状态。
- V2 原有工作状态保持不变。V3 尚未启动，复制不代表运行环境已隔离或客户功能已经可用。
- 用户进一步明确：V2、V3 不同时启动，要求交替使用且互不改写。保留原端口和使用方式，不为两个版本建设并行部署体系。

### 1.1 最小增量原则（用户已确认）

1. **直接沿用。** 工作台、登录、角色权限、任务与历史、模型配置、个人／平台 Cookie、初稿确认及已有交付机制继续使用；不为神州另建同类系统，不重新设计通用操作流程。
2. **增加场景。** 在现有自然语言意图识别和任务执行链中承载银行、客群、时间、字段和交付要求，不新增必选模板步骤；自动补搜、OCR 递补及本场景不生成分析报告等规则限定在该场景，不能改成其他任务的全局默认行为。
3. **补齐缺口。** 日期／图片等字段传递、笔记评论关联、OCR 结果接入和结构化导出等缺口，先复用现有组件，确有不足才修改对应模块。通用模块的修正保持已有调用兼容，不顺带重构。
4. **验证增量。** 验收同时证明神州场景可用与被改动的通用路径没有回归；保留 V2 原目录不动。计划中的阶段只是同一场景的实现顺序，不代表要新增多套子系统。

### 1.2 按用户 query 执行（用户纠正后的首要业务原则）

- 先理解用户本次要什么，再选择场景和执行规则。用户明确的主题、客群、时间及内容要求优先于场景业务默认值；默认值只补充未说明的部分，不覆盖既有权限和数据访问边界。
- 来源选择保持现有逻辑：未明确要求小红书的任务不强制转入小红书专属路径。明确“小红书 + 银行权益”的任务默认包含图片识别及权益字段抽取，无需用户逐次重复提出这些处理步骤；广义私银资料及其他非权益任务保持其自身 query 范围。
- 用户说“采集私银相关资料”，就按私银相关数据和内容理解，不擅自收窄成必须包含某类权益或指定字段；用户说“私银权益的门槛和次数”，才把这些具体规则作为本次重点。非权益类资料需求沿用适合的通用任务路径，不能仅因出现“银行／私银”就强套权益抽取流程。
- “符合要求”以本次 query 的实际目标为准。没有用户要求时，不额外设置“权益名称加至少一项门槛／次数／积分／有效期”的硬门槛，也不能因为缺少附件中的部分字段就排除相关内容。字段缺失仍如实记录，相关性与字段完整性分开表达。
- 已确认的银行权益场景预算和自动递补规则保留；补搜、筛选与停止所依据的相关性和内容要求来自本次任务。用户明确提出不同数量或范围时，应在任务参数中体现并沿用既有任务修订机制，不能为了套用默认规则静默改写 query，也不能在执行中自行突破冻结上限。

## 5. 最小可验收业务流程

1. 用户在现有 `/data-prep` 工作台直接用自然语言提出需求，不要求选择模板。未指定来源时沿用通用来源选择逻辑；明确要求小红书银行权益时，识别该场景并默认执行图片识别和权益字段抽取，同时保留原始内容与证据。所有已登录用户可用，沿用现有登录、Owner、个人设置、任务历史及代跑操作；本期不另建客户门户或场景权限系统。
2. 冻结原关键词、银行列表、客群范围、图文类型、排序、日期范围、每家银行的候选及 OCR 额度和评论范围。未指定客群时默认覆盖各类零售客群并分类呈现；明确指定时定向筛选。默认日期为执行当年 1 月 1 日至任务冻结时；本机和服务器统一记录时区。
3. 按所选凭证排队，首批搜索 20 条候选，按 note_id 去重并获取详情。符合要求的帖子不足 5 篇时自动补搜，累计最多检索 100 条候选；记录检索数量、去重数量和实际可用数量，达到上限或来源耗尽仍不足时如实说明。
4. 保留笔记、作者必要字段、所有图片顺序与评论关系。评论总数、实际获取数、回复截断或获取失败分别记录；回复必须有明确上限，不能默认无限展开。
5. 平台依据已获取的正文、时间、客群、公开来源证据和评论自动初筛；获取所选帖全部图片的可复核副本，并送入现有图片解析组件。图片识别后发现规则过期或客群不符时自动递补；必要时回到搜索步骤补充候选。累计最多识别 20 篇帖子的全部图片，得到 5 篇符合要求的帖子后提前停止；识别失败的帖子也计入已尝试篇数，不能通过失败重试规避范围上限。
6. 从正文、图片及已获取评论抽取单帖权益、表格和证据，标记过期／客群不符／营销／倒卖／提问，并在已有证据范围内复排。
7. 同一冻结结果生成 Excel、JSON、图片证据包与字段缺失说明，先通过现有 Owner 隔离入口提供可下载初稿并停下等待用户。用户核对并确认后，沿用既有流程进入正式交付；人工确认不替代完整性与 QA 门。初稿文件和正式结果的状态必须清楚区分，不能将中间 JSON、OCR 成功或仅人工采纳当作已经正式发布。

### 5.1 自动初筛、递补与停止条件

先按本次 query 判定主题、客群、时间和所需内容是否匹配。银行权益场景的缺省排序顺序为时间适用性、客群匹配、规则证据强度、来源可信程度、评论中的具体规则；热度仅作辅助。不新增综合加权分数，保留排序理由。不以用户未要求的规则字段完整性作为统一准入门槛。

尚未识别图片时，无法准确比较全部候选的图片证据。采用用户已确认的自动初筛和递补，识别后在已有证据范围内复排；没有识别的图片标记未识别，不能声称已找出全部候选中业务上最优的 5 篇。

每家银行分别冻结三个数量：首批候选 20 条、累计候选上限 100 条、累计 OCR 上限 20 篇；每家目标为 5 篇符合要求的帖子，每篇识别全部图片。某家满足目标即停止该银行的新增检索和 OCR；不能达到目标时，遇到该银行 OCR 上限，或候选预算耗尽且已有候选无法继续补足时结束该银行的处理，保留实际结果、排除及失败原因。各银行分别完成或达到停止条件后结束整个任务，不因一家不足或达标而停止其他银行。扩大已确认上限需要新的显式任务修订，不自动突破。

### 5.2 时间和有效性

- 帖子发布时间、更新时间、采集时间及权益有效期是不同字段，不互相覆盖。
- 旧帖和过期规则保留在候选证据中并标记，不混入当前有效推荐；日期未知单独呈现。
- 图片出现已到期规则，即使帖子较新也不能直接标为当前有效；一帖多项权益的有效期分别记录。
- “今年”“每季度”等相对表达保留原文，只有可靠上下文足够时才规范化；不能用今天补造缺失年份。

### 5.3 图片和表格

- App 截图分类遵循附件的界面特征及银行语义要求；线下公告单独分类，不能仅凭 Logo 当作 App 截图。
- 表格保留表头、行列、客户层级、次数、周期和合并条件。识别不可靠时保留原图、文本及待复核标记。
- 例如四类权益乘以五个等级不直接计成 20 个独立权益；“两项中选一、每季一次”不能拆成每项各一次。
- 长图可在解析内部按需要分段，但交付必须能定位回原图；局部失败不能伪装为全图已识别。

## 6. 输出契约

先固定一个场景数据契约，再由它生成两类交付，避免 Excel 和 JSON 分别抽取、内容不一致。

| 层次 | 最少需要表达的内容 |
|---|---|
| 任务 | 冻结参数、执行时间、各阶段状态、实际数量、缺失原因和契约版本 |
| 笔记 | note_id、公开 URL、原始标题／正文、日期、作者必要信息、互动量、标签和排序理由 |
| 图片 | note_id、图片序号、原始来源、证据文件引用、获取与识别状态、文本及表格块 |
| 评论 | note_id、comment_id、parent_comment_id、原文及必要公开字段；不附加头像／IP 等排除信息 |
| 权益 | note_id 下的权益项目，银行／客群／类别／名称／门槛／次数／积分／有效期；支持多条 |
| 证据定位 | 原文片段、图片序号及区域／表格行列／评论 ID；原始事实与模型判断分开 |

建议 Excel 包含“笔记清单、权益明细、评论、图片识别、执行说明”五张表；图片文件通过证据引用关联。复杂表格结构以 JSON 保真，Excel 提供可核对的表头与单元格展开，不强行压进笔记的一格文本。

JSON 使用相同字段语义及稳定 ID，保留一帖多权益、多图片、多评论关系。通过现有鉴权和任务结果接口接入，补充本场景稳定契约；不另建一套鉴权或 API 平台。

缺失值使用 null 并给原因，例如源站未提供、未采集、识别失败、证据不足；不能以 0、空字符串或 false 假装有效数据。抽取字段须可回溯；模型不能补造银行规则。

原始第三方记录不能不经筛选透传给模型或导出。特别是 note_url 的认证查询参数和底层 xsec_token 应留在受控访问边界，交付只给公开定位信息。平台公用 Cookie 不向客户展示其原值，也不允许共享业务结果或浏览器上下文。

图片保留周期、清理策略和权限沿用平台任务资料边界；如果现有策略无法满足人工复核，则在实施前明确留存要求，不自行假定固定天数或永久保存。

## 7. 本机、公网和 10 人使用

### 7.1 V3 启动前的隔离

初次核对发现 V3 `.env` 中 `MEDIACRAWLER_PATH`、`MEDIACRAWLER_PYTHON` 仍指向 V2。随后根据用户关于独立副本的要求，已将这两项改为 V3 对应位置：目标目录存在，V3 解释器启动检查通过，`sys.executable` 与 `sys.prefix` 均属于 V3，V2 `.env` 修改前后哈希一致。未启动平台或采集服务；数据库、下载目录、日志、模型配置及运行端口仍需在实际启动前核验，不能据此宣称运行时已完全隔离。

先验证 V3 的读写和进程归属，再启动 V3。不得让 V3 的清理或停止操作影响 V2；复制得到的数据库和账号不能未经审视直接作为公网客户实例启用。

交替使用的本机调整已完成：V3 启动脚本先进入自身目录；SearXNG 使用 V3 专属容器名及 Compose 项目，Firecrawl 使用 V3 专属 Compose 项目，启动与停止脚本名称一致。镜像和端口维持原设置，RSSHub 保留现有共享服务方式，不进行镜像升级或共享服务配置变更。独立项目避免切换版本时替换另一个版本的 Compose 实例或沿用其项目目录挂载。

本次只读验证：两个版本的 WebUI／Scheduler 数据库启动预检均通过；V3 两份 Compose 配置均能解析，解析后的挂载无 V2 路径；修改涉及的 V2 对应配置文件哈希未变，批处理保留 CRLF。没有启停服务或执行数据库迁移，因此这些结果不代表已完成 V3 全功能运行验收。实际使用时先用当前版本的停止脚本结束运行，再用目标版本目录中的启动脚本启动；交替共用同一浏览器地址时应刷新页面并重新登录。

### 7.2 小规模多用户调度

- 支持最多 10 人同时提交任务，并不承诺同一小红书账号同时进行 10 路采集。
- 建议平台公用 Cookie 初始按单个采集任务串行排队；个人 Cookie 按实际凭证隔离调度。同一凭证重复配置也不能绕过共享限制。
- 复用现有任务管理、取消和状态显示，补有界排队与超时回收；当前没有证据需要新增 Redis 或独立调度平台。
- Cookie 失效、验证码、访问受限时明确提示并保留进度，用户处理后恢复；不自动绕过验证，也不静默换号。
- 本机和公网实例若使用同一个实际平台账号，同样存在跨实例竞争。首期应避免同时采集，或给环境使用不同授权账号；若必须同时共用，才评估跨实例协调。

### 7.3 部署证据

本机用于开发和验证，公网实例用于双方使用；复用私有成员制、HTTPS、角色权限和审计。服务器硬件、系统、网络及 OCR 服务部署位置尚未核实，当前不承诺吞吐或响应时间。

10 用户验证先使用模拟采集器测队列、取消、Owner 隔离和资源上限，不向小红书做并发压力测试。之后在授权和凭证正常的前提下做受控真实验收。

## 8. 实施顺序与阶段产物

当前只完成第 0 阶段的方案材料，后续阶段须在方案确认后推进。此处编号不是 Excel 的 P0／P1／P2。

| 阶段 | 最小工作范围 | 退出条件 |
|---|---|---|

### 9.1 业务案例

| 案例 | 必须证明的行为 |

| 官方中信会员海报及账号页 | 正文、全图、官方认证证据各自记录；排除企业全称和统一社会信用代码 |

| 招行积分贵宾厅案例 | 不混淆积分体系；地点、兑换消耗、获得规则分别保存 |

| 缺失日期／失败图片／失效链接 | 状态和原因明确，不补造值，不假装完成 |

### 9.2 工程与真实任务

- 复用现有社媒隔离、图片解析、来源及交付测试，补字段丢失、评论关联、参数传递、凭证排队和本场景禁报告的针对性回归。
- 专属场景的两个真实查询可使用“采集小红书上的中信银行权益”“采集小红书上的招行贵宾厅权益”，明确任务时间范围；不指定来源的版本用于验证通用来源选择不受影响。截图中的历史帖子不因出现在附件中而自动纳入当年结果。
- 首批 20 条候选、自动补搜最多 100 条；OCR 不合格自动递补，累计最多 20 篇且逐篇全图，取得 5 篇符合要求的帖子后提前停止；每帖前 20 条一级评论与受限回复。覆盖首批满足、补搜满足、OCR 后递补、候选耗尽、OCR 达上限等停止分支；实际不足或失败均有清单。
- Excel 与 JSON 的 ID、数量、字段值及证据一致；所有交付排除项无泄漏，尤其 Cookie／Token／IP／头像等。
- 权限验证覆盖跨 Owner 列表、详情、下载和取消；管理员查看业务正文遵守原平台审计边界。
- 10 用户模拟中队列可见、共享凭证按约束执行、个人任务隔离、取消释放资源；同凭证跨环境竞争也有明确处理。
- 正式结果可定位回原文、图片或评论；部分 OCR 失败不能用整体成功状态掩盖。
- 初稿可下载并明确标识，初稿生成后停止；未经用户确认不能正式交付。确认后仍遵守既有完整性和 QA 条件，重复确认不能造成重复发布。
- 自然语言任务可进入该场景，不需选择模板或新增账号授权；未指定客群时不多问一次必填客群，也不误标客群不符。多银行任务分别执行每家额度和停止条件，不因一家达到目标而截断其余银行。
- 来源与处理深度验证：“采集中信私银权益”沿用通用来源选择，不能擅自限定小红书；“采集小红书上的中信私银权益”默认执行图片识别及字段抽取，不额外要求用户勾选 OCR；显式限制只采原始内容时遵循该限制。
- query 范围验证覆盖“私银相关资料”“私银权益的门槛和次数”“信用卡权益”及明确历史时间范围：分别遵循用户本次要求，不强套同一字段门槛，不用缺省信用卡或当年规则覆盖明确指令；非权益任务保持通用路径可用。
- 用人工标注样本评估字段准确率与覆盖率，不预先宣称 OCR 或规则抽取达到 100%。工程测试通过与客户验收分别记录。

## 10. 实施前仍须核实的事项

这些事项不阻塞当前方案编写，但不能在进入相应实施／部署阶段时被忽略。

1. **采集器使用授权。** 当前本地 MediaCrawler 许可证限制未经书面同意的商业用途。神州客户服务前应核实是否已有书面授权，或改用许可适配的数据来源；本次未见授权材料，不推断一定没有授权。官方依据：[MediaCrawler LICENSE](https://github.com/NanmiCoder/MediaCrawler/blob/main/LICENSE)。不将购买任何产品名称自动等同于获得本项目适用许可。
2. **V3 实际启动。** 两项采集器路径及 Compose 项目隔离已修正，解释器与两个版本的数据库启动预检通过；未启停服务。实际切换启动后仍须验证读写目录、进程归属及基本功能，静态检查不能代替运行验收。
3. **OCR 和公网环境。** 确认现有服务可达、模型适合长图表格、图片处理的数据去向满足已有外发边界；服务器规格和真实吞吐待测。
4. **真实来源可获取程度。** 日期、认证字段、正文完整性、全部图片和回复的当前可获取程度须用授权样本核实，源码映射不等于平台接口持续稳定。
5. **历史试跑对照。** 若要证明相对历史试跑的改善，需要原始 `data.json`；没有原文件时仅按工作簿摘要对照，不伪造基线。

当前方案不要求重新建设账号配置、通用权限、完整工作台、OCR 引擎或导出引擎；重点是补齐社媒数据传递与关联，将银行业务规则和可复核交付接到已有平台上。
