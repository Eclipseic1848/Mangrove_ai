# ADR-0052：两条旧 Chat 的独立补充隔离

- 状态：accepted
- 日期：2026-10-28
- 来源：#285；用户选择限定风险接受，批准同票补充 PR、必要显式迁移与一次受控切换例外。
- 关系：补充 ADR-0051；原首次隔离的固定清单和不可变合同继续有效。

## 问题与范围

现役服务出现两条未纳入首次隔离的 `chat/cleanup_failed` 绑定。没有可靠历史终点，也没有
适用于旧 Chat 的 RunSeal；空活动计数不能证明旧工作自然结束。直接清状态、扩充原清单或
重发都不成立。用户只接受这两条保持未知、暂不可恢复；不禁用整个账号，不自动处理其他异常。

## 决策

显式迁移 `webui_0026` 初始化独立键 `deployment.supplemental_chat_quarantine`。
复用固定原件摘要和身份格式，非空只接受两条明确 Owner、Chat ID、代数的 `cleanup_failed`
绑定及对应两个原件。登记需要有效超级管理员、固定审批与风险接受，在真实维护停机和双库
锁内执行；清单一旦固定不可修改、删除、追加或清空，精确重放幂等。原首次隔离设置不变。

执行与账号停止核对读取两批目标，但审批、计数与摘要分批呈现；部署只排除原件吻合的精确
补充绑定，任何第三条异常仍阻断。原 Chat 的冻结模型运行在恢复入口、Grant 发行和 Relay
读取处拒绝，不能利用恢复中新建的 Chat ID 重发旧工作。其他独立新任务和真实用量记录保持。
数据库触发器保护补充清单和原绑定，拒绝迟到更新、删除、换 Owner 及 REPLACE。

该隔离不是停止证明。首次加载此补充批次时，旧服务允许一次例外：暂停新领取，确认当前
活动归零、仅固定两条仍阻断且其他项全部通过后正常停服。保留原 `quiet=false`，不伪造旧版
sealed 回执。备份、独立恢复、异机副本完成后才迁移并登记；新实例必须实际严格封口通过。

## 验证与回退

必须验证原清单与原记录保留、两条执行/恢复/Grant/迟到写拒绝、新独立工作可用、错配与第三条
异常仍阻断、迁移副本与恢复一致。服务器真实数据、来源与三端一致另按工单回执验收。

回退代码必须识别两份隔离，并保留新库和新增业务；禁止直接启动忽略新隔离的旧版，禁止
回灌旧库抹掉登记。切换前须准备并演练此兼容路径。此决策不新增通用自动隔离、产品运维
界面或 Cookie 工具，不移动现有版本标签。
